### Contrats des commandes de clés (tous formats) pour l'interface

toutes les pages, le plus récent d'abord ; `refresh` relance les sources MCP au lieu de relire leur dernière réponse ; une source en échec est dans `errors` avec son id et son message, les autres donnent quand même leurs tickets) ; `sources` : ids ci-dessous) ; `tickets_resolve {input, project?}` → `Resolution` (`input` : URL d'issue, `owner/repo#42`, `<dépôt>#42`, `#42`, URL Jira ou clé `ACME-123`, URL ou clé d'un ticket listé par une source MCP ; une copie MCP d'un ticket GitHub ou Jira va à la source native) ; `tickets_run {input, project?, repo?, cols?, rows?}` → `Run` (résout, lit le ticket, crée worktree et branche, ouvre la session Claude Code et émet `session-opened` ; `repo`, nom ou chemin, est requis quand `Resolution.repo` est vide) ; `tickets_runs` → `[Run]` (le plus récent d'abord) ; `tickets_events {id}` → `[RunEvent]` ; `tickets_deliver_preview {id}` → `DeliveryPreview` (ce que la livraison enverrait, à montrer avant) ; `tickets_deliver {id, confirm}` → `Delivery` (la gate humaine, avec le `fingerprint` de l'aperçu validé : commit de exactement ce que l'aperçu listait, push, PR ; refusé si le worktree a changé depuis l'aperçu ou s'il n'est plus sur la branche du run ; relivrer pousse ce qui a changé et retente le commentaire du ticket) ; `tickets_close {id, force?}` → `Run` (refusé s'il reste du travail non poussé, sauf `force`, qui garde alors la branche ; arrête la session du run avant de retirer le worktree ; l'erreur est un objet `CloseError = {kind: "uncommitted"|"unpushed"|"error", message, uncommitted, commits}` : `uncommitted` = des changements non commités, `unpushed` = seulement des commits non poussés (`commits`), `error` = autre chose) ; `open_url {url}` ouvre une adresse `http(s)` dans le navigateur du système (`open`, `xdg-open`, `explorer` ; aucun shell ; refusé : autre schéma, espaces, guillemets, caractères de contrôle). Événement `run-updated` (`Run`) à chaque changement d'un run.

Données : `<data>/termf.db` (SQLite, WAL), `<data>/runs/<id>/{journal.md, events.jsonl}`, worktrees dans `<dépôt>/.claude/worktrees/termf-<run>-<branche sans termf/>` (ARCHITECTURE §9 : la session hérite de la confiance de Claude Code dans le dépôt ; `/.claude/worktrees/` ajouté une seule fois à `.git/info/exclude` du dépôt), ou `<data>/worktrees/<projet>/<run>/<dépôt>` avec `worktrees = "data"` et pour les runs créés avant. CLI : `termf run | runs | inbox | deliver [--yes] | close`. Détails : `app/src-tauri/src/tickets.rs`, `crates/termf-tickets`.

### Contrats de la reprise des runs, du nettoyage après merge et de l'inbox économique (suites de la phase 3)

Reprise : `tickets_resume {id, cols?, rows?}` → `{run: Run, warning?}` (ouvre une nouvelle session dans le worktree du run avec `claude --resume <conversation>`, le même environnement que la première : ports et variables de la dernière préparation, sans la relancer, garde-fou `termf guard`, `--disallowedTools`, `--add-dir` du brief, bibliothèque du projet ; émet `session-opened` puis `run-updated`) ; refusée si le run n'est ni `running` ni `delivered`, si son worktree a disparu, s'il a été lancé avant cette version (pas de conversation connue), si une reprise du même run est en cours ou si une session de TermF tourne encore dans cette conversation (celle du run, ou une tuile dont les hooks donnent ce `session_id`) : jamais deux processus sur une conversation. Que Claude Code ait encore la conversation n'est qu'un indice (le `$CLAUDE_CONFIG_DIR` du shell de l'agent peut différer de celui de TermF lancé depuis le Dock) : sans `<dossier Claude>/projects/*/<conversation>.jsonl`, la reprise part quand même avec un `warning` (« may no longer have the conversation »), et c'est la session elle-même qui dit si la conversation n'existe plus. Au lancement, TermF génère l'UUID et le passe par `--session-id` ; à chaque `SessionStart` d'une session de run, la conversation enregistrée suit (`/clear` en ouvre une nouvelle, la remise à zéro du contexte aussi). CLI : `termf run resume <run>` (par l'app, comme `termf run` ; le `warning` sur la sortie d'erreur ; ni `--project` ni `--repo`). Le garde-fou refusait déjà `termf run …` dans la session d'un run.
Nettoyage après merge : `tickets_check` → `PrCheck = {cleanups: [Cleanup], errors: [{run, message}]}` (à appeler à l'ouverture de la vue Tickets : demande à GitHub l'état de la PR de chaque run `delivered` dont le sort n'est pas encore connu, par `GET repos/<owner>/<name>/pulls/<n>` avec ETag ; l'app le fait aussi 30 s après le démarrage puis toutes les 15 min ; sans run livré à PR ouverte, rien ne part sur le réseau ; `cleanup = "off"` : rien du tout ; `errors` : les runs dont GitHub n'a pas pu dire l'état de la PR, redemandés la fois suivante, aussi écrits dans le journal de l'app pour la vérification de fond) ; `tickets_cleanup {id}` → `Run` ou `CloseError` comme `tickets_close` sans `force` (refusé tant que la PR est ouverte (une PR connue fermée est redemandée, elle a pu être rouverte : son état est alors oublié), qu'il reste du travail non commité ou des commits non poussés ; arrête la session, teardown de la préparation (copie de base, ports), retire le worktree et la branche locale ; marche quel que soit `cleanup`, c'est l'action explicite). Événement `run-cleanup` (`Cleanup`) pour chaque PR trouvée mergée ou fermée, une seule fois, avec `run-updated` ; l'interface en fait la notification (rien côté backend, les textes restent dans `i18n.ts`). `Cleanup = {run: Run, cleaned, error?}` (`cleaned` : TermF a fermé le run ; sinon il attend `tickets_cleanup`, et `error` dit pourquoi TermF n'a pas pu, par exemple du travail non commité en mode `auto`). Config : `[tickets] cleanup = "auto"|"ask"|"off"` dans `termf.toml` (défaut `ask` : la PR mergée est signalée, la clôture reste à l'utilisateur ; `auto` : TermF ferme le run si rien ne serait perdu, une seule tentative).
`Run` gagne `claudeSession?` (la conversation Claude Code que la reprise prendra ; absent pour un run d'avant cette version, qui ne se reprend pas) et `prState?: "merged"|"closed"` (connu une fois la PR mergée ou fermée : le run est alors « prêt à nettoyer » tant qu'il est `delivered` ; oublié à chaque nouvelle livraison, qui le fait redemander). `RunEvent` gagne `session_resumed {session, conversation}`, `pr_merged {url}`, `pr_closed {url}`. Base : colonnes `claude_session` et `pr_state` ajoutées à `runs` à l'ouverture (`user_version = 3`), écrites seulement par des mises à jour ciblées (jamais par la réécriture d'une copie du run, pour qu'une livraison ou une fermeture en cours ne défasse ni un `/clear` ni un merge) ; `pr_state` et l'événement `pr_merged`/`pr_closed` dans une même transaction, seulement si le run est encore `delivered` et que l'état n'est pas déjà connu (deux vérifications simultanées l'enregistrent une fois). Dans l'app, vérification et `tickets_cleanup` passent l'une après l'autre. La dernière préparation garde aussi son environnement dans `<dossier git du worktree>/termf-setup.json` (`env`).
Inbox : GitHub Issues (avec ou sans projet) lit chaque page de `search/issues` (100 par page, au plus 10) par `gh api --include` avec l'ETag de la dernière réponse (`If-None-Match`) ; un 304, qui ne coûte rien sur le quota, rend la réponse gardée. Cache en mémoire par requête et par page dans l'app (le `Tickets` partagé ; la CLI repart de zéro à chaque commande), 256 requêtes au plus. `refresh: true` demande sans ETag (relecture complète) et relance toujours les sources MCP ; sans `refresh`, les sources MCP répondent de leur cache comme avant. GitHub Projects v2 reste lu par `gh api graphql`, que GitHub ne sert pas en requêtes conditionnelles (choix validé : pas de passage à l'API REST des Projects) ; Jira et MCP inchangés.
Interface (vue Tickets) : `tickets_check` à chaque ouverture de la vue ; `watchTickets()` (`tickets.svelte.ts`, lancé par `+page.svelte`) suit `run-updated` et notifie chaque `run-cleanup` (textes `ticketsUi*` de `i18n.ts`) ; la session d'un run est `Run.sessionId` (si elle tourne encore) ; « Reprendre » pour un run `running` ou `delivered` sans session vivante, avec `claudeSession` et un worktree ; « Prêt à nettoyer » = `delivered` avec `prState` ; aide « question de confiance » quand la session du run reste `starting` plus de 6 s (TermF ne répond jamais à cette question). Logique pure testée par `pnpm test` : `lib/tickets-logic.ts` (`liveSession`, `readyToClean`, `resumable`, `refusal`, `cleanupNotice`).

### Contrats des sources de tickets (section « Tickets » de l'éditeur de projet)

`tickets_sources {project}` → `Sources = {trackers: Trackers, jiraToken, githubRepos, mcpTools}` (`jiraToken` : le trousseau a un jeton pour le site et l'e-mail de `jira` ; `githubRepos` : `owner/name` des dépôts GitHub du projet, ceux que lit GitHub Issues ; `mcpTools` : par source MCP, les outils de lecture que TermF connaît pour son serveur) ; `tickets_sources_save {project, trackers}` → `Sources` (écrit `[trackers]` du projet en gardant commentaires et clés inconnues, sans écrire les valeurs par défaut ; aucune source = un `[trackers]` vide ; oublie la dernière réponse des seules sources MCP dont les réglages ont changé ; refuse un tableau, un site, un e-mail, un nom d'outil ou de source invalide ; l'éditeur ne l'appelle que si les sources ont changé) ; `tickets_source_test {project, trackers, source}` → au plus 5 `TicketSummary` (`trackers` tel que l'éditeur le tient, enregistré ou non ; rien n'est mis en cache) ; `tickets_jira_token {site, email}` → `bool`, `tickets_jira_token_save {site, email, token}` et `tickets_jira_token_forget {site, email}` (trousseau du système, service `dev.termf.tickets`, compte `jira:<site>:<email>`, jamais dans la config, la base ni les erreurs) ; `tickets_mcp_servers {project?}` → `[{name, status, tools}]` (`claude mcp list` depuis le premier dépôt du projet, lent : il vérifie chaque serveur ; `status` tel que Claude Code l'écrit ; `tools` : outils de lecture connus, vide = à lister).
`Trackers = {github?: {repo?, comment, issues, project?, columns, mine, transition?}, jira?: {site, email, jql?, project?, comment, transition?}, mcp: {<nom>: {server, tools, prompt?}}, implicit}`, les mêmes clés dans le TOML du projet (sauf `implicit`, en lecture seule : le projet n'a pas de `[trackers]` et lit donc, comme avant les sources, GitHub Issues sur les remotes GitHub de ses dépôts ; enregistrer les sources les écrit) :
- `[trackers.github]` : GitHub Issues (issues ouvertes assignées dans les dépôts du projet et `repo` ; `issues` vrai par défaut sauf si `project` est indiqué ; sans dépôt GitHub, la source est ignorée) et, avec `project = "owner/numéro"` (ou l'URL du tableau), GitHub Projects v2 via `gh api graphql` : issues ouvertes du tableau, non archivées, dans `columns` (valeurs du champ Status, toutes si vide), assignées à toi si `mine` (vrai par défaut) ; `transition = "<Status>"` déplace l'issue sur le tableau à la livraison (rien par défaut ; `gh auth refresh -s project` peut être nécessaire).
- `[trackers.jira]` : Jira Cloud, API REST v3 par `curl` (aucune pile HTTP/TLS ajoutée ; jeton passé sur l'entrée standard de curl, `--disable` ignore `~/.curlrc`) ; `site`, `email`, `jql` (défaut `assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC`, pagination `nextPageToken` de `/rest/api/3/search/jql`), `project` (préfixe de clé accepté pour une clé collée seule ; sans lui, toute clé va au projet), `comment` (lien distant vers la PR à la livraison) et `transition` (statut ou transition à la livraison), tous deux désactivés par défaut. Description et commentaires ADF convertis en Markdown.
- `[trackers.mcp.<nom>]` : `server` (nom dans `claude mcp list`), `tools` (noms courts, sans motif ; vide = outils de lecture connus pour Atlassian, GitHub, Linear), `prompt` (quoi chercher, facultatif). Lecture par `claude -p --output-format json --json-schema <schéma> --model haiku --max-budget-usd 0.25 --tools "" --allowedTools mcp__<serveur>__<outil>,… --permission-mode dontAsk --permission-prompts none --restricted --settings '{"disableAllHooks":true}' --disable-slash-commands --no-session-persistence` depuis le premier dépôt du projet : aucun outil intégré, seuls les outils listés, tout le reste refusé sans personne pour l'accepter, ni réglages (donc ni règles `allow`) de l'utilisateur ou du dépôt, ni hooks, skills ou commandes. Réponse revalidée (schéma strict, clé, URL `http(s)` sans espace ni guillemet, tailles) puis refusée en bloc au moindre écart ; mise en cache dans `termf.db` (table `listed`) jusqu'au prochain `refresh` ; le ticket lu pour un run est encadré comme donnée comme les autres. Une source MCP est en lecture seule : ni commentaire, ni transition, ni lien.

Réponse absente ou invalide, erreur de l'agent ou écart bloquant : une seconde tentative (nouvelle session, le motif en retour), puis l'étape est bloquée ; rapport `blocked` ou `failed` : bloquée tout de suite. Une tâche travaille dans son propre worktree détaché `<data>/team/<run>/<tâche>`, créé depuis le HEAD du worktree du run ; à la fin, TermF commite (`<ticket> <tâche>: <but>`, identité git de l'utilisateur, hooks du dépôt compris), applique les contrôles (un marqueur de conflit laissé fait échouer le commit), fusionne dans le worktree du run puis retire le worktree de la tâche ; en cas de conflit, TermF fusionne le travail du run dans le worktree de la tâche, y laisse le conflit, mesure désormais la tâche depuis ce travail et relance son agent pour le résoudre (correction automatique, puis toi). Budget du run : coût = somme des sessions de ses étapes ; dès qu'il l'atteint, ses agents sont arrêtés et l'équipe passe en `budget`. Reprise : au démarrage de l'app, une équipe qui travaillait passe en `paused` (rien ne dépense sans toi) ; `team_start` reprend chaque étape en cours : son tour fini est traité, sinon sa conversation reprend (`--resume`) avec un message « continue » ; avec un nouveau budget, elle repart plutôt dans une nouvelle session (avec ce message en retour, sans compter comme correction), dont le plafond suit le nouveau budget.
Règles (§7.6) : niveau de chaque règle = le sien si la bibliothèque l'active (sinon `off`) → `[rules]` de `termf.toml` → `[rules]` du workflow → `[rules]` du projet → ticket (`options.rules`, `team_rules` sans tâche) → tâche ; une règle d'un dépôt reste `off` tant qu'elle n'est pas activée. Les niveaux vont aux sessions (`rules`, donc dans leur prompt), et les contrôles des règles qui visent le rôle (`applies_to`) au niveau `warn` ou `block` tournent à la fin de chaque tâche : `scope` (fichier hors des `writes` du rôle, ou hors des `files_hint` de la tâche sans être cité dans le rapport ; diff de plus de 200 / 800 / 3000 lignes pour S / M / L : signalé seulement), `text-changes` (heuristique ligne à ligne sur `git diff -U0` : littéraux qui se lisent comme du texte, texte entre balises, valeurs `alt` / `title` / `placeholder` / `aria-label`, lignes Markdown, valeurs des traductions json / yaml / po, commentaires existants modifiés ; un texte retiré et ajouté dans le même fichier n'a fait que bouger ; tests, snapshots et lockfiles exclus ; justifié s'il figure dans le ticket ou dans `report.text_changes`), `ui-changed` (tsx, jsx, vue, svelte, css, scss, html…, traductions, `ui_impact` ou `affected_views` : la gate visuelle). `block` fait échouer l'étape (correction automatique puis toi), `warn` signale (événement `violation`, `Step.violations`, résumé à l'étape `rules`), `advise` ne fait qu'injecter les consignes.
Données : `<data>/termf.db` (tables `team_runs`, une ligne JSON par run écrite seulement par l'app, et `team_events`), lignes `team` ajoutées à `runs/<id>/journal.md`, worktrees des tâches dans `<data>/team/<run>/`. CLI : `termf team ls | plan <run> | run <run> [--workflow <nom>] [--rule <règle>=<niveau>]… [--budget <usd>] | status <run> | events <run> [--after <n>] | approve <run> <étape> | revise <run> <étape> <retour>… | rules <run> [--task <id>] <règle>=<niveau>… | stop [<run>]` (`ls`, `status` et `events` lisent la base, sans l'app). `vault_reveal {name, scope, project?}` → la valeur (la seule commande qui en donne une ; une référence est résolue par la CLI de son gestionnaire, 2 min au plus pour elle et sa sortie ; depuis l'app, avec le `PATH` du shell de connexion et les seules variables de ce gestionnaire qui manquent à l'app, lues dans ce shell : `OP_ACCOUNT`, `OP_SERVICE_ACCOUNT_TOKEN`, `OP_CONNECT_HOST`, `OP_CONNECT_TOKEN`, `OP_CONFIG_DIR` ; reprise dès que `termf.toml` change, synchro comprise). Événement `vault-status` (`Status`) dès que le coffre se verrouille de lui-même (inactivité, veille), quelle que soit la commande qui l'a vu, et après `termf vault unlock|lock`. Chaque changement (création, déverrouillage, ré-authentification, écriture, référence, suppression) n'a lieu qu'une fois son entrée d'audit écrite ; un verrouillage n'est jamais refusé. Types : `Scope = "dev"|"staging"|"prod"` ; `Status = {initialized, unlocked, remembered, autoLockMinutes, prodUntil?}` (`prodUntil` : secondes Unix jusqu'auxquelles prod ne redemande rien) ; `SecretInfo = {name, scope, project?, description, created, updated, reference?}` (jamais de valeur) ; `name` : lettres, chiffres, `_ . -`, commence par une lettre ou `_`, 128 au plus ; `Entry = {id, at, actor: {kind: "human"|"agent"|"termf", run?, session?}, action, target?, scope?, project?, size?, masks?, detail?, prev, hash}` avec `action = "init"|"unlock"|"unlock_failed"|"lock"|"reauth"|"reauth_failed"|"write"|"reference"|"delete"|"reveal"|"read"|"resolve"|"refused"` (`lock` par `termf` : `detail` `idle` ou `sleep` ; `resolve` : `detail` `reveal <uri>` ou `use <uri>`) ; `Verification = {ok, entries, broken?, error?}`. Références : `op://coffre/élément[/section]/champ` (`op read`), `bw://élément[/password|username|notes|totp|uri]` (`bw get`), `doppler://projet/config/NOM` (`doppler secrets get --plain`), `aws-sm://id` (`aws secretsmanager get-secret-value`, `SecretString`), `vault://chemin#champ` (`vault kv get -field`).
Pour les tranches suivantes (crate `termf-vault`) : `Vault::value(actor, id, Access::Use)` donne une valeur à utiliser pour l'utilisateur ou un agent (audit `read` / `resolve`), jamais à montrer ; `Access::Reveal` est refusé (et audité) pour un agent ; prod demande toujours la ré-authentification ; `Vault::masker()` → `Masker` (les valeurs du coffre de 4 caractères ou plus, et, d'une valeur sur plusieurs lignes, celles qui ressemblent à une clé : 16 caractères ou plus, base64 ou aléatoires, jamais l'armure `-----BEGIN …`), `Masker::add` pour une référence résolue, `Masker::mask(text)` → `{text, count}`, puis `termf_claude::mask::mask_text` ; `Vault::record(Event)` ajoute une entrée d'audit (`size`, `masks`, `detail` pour `ops.run`) ; `harden_process()` coupe les core dumps ; `Vault::on_lock(f)` prévient quand il se verrouille de lui-même. API locale : `Call::Vault` = `status | unlock {password} | lock` seulement, jamais une valeur ni un nom (un agent peut lire le jeton, §4). CLI `termf vault …` (voir `termf help`) : chaque commande qui lit ou écrit un secret demande le mot de passe maître sur le terminal et ouvre le fichier elle-même, sans jamais passer par l'app ni par le trousseau. Sessions Claude Code lancées par TermF : `termf_core::claude::SECRET_DENY` (`Read(**/.env*)`, `Read(**/*.pem)`, `Read(**/id_*)`, `Read(//proc/**/environ)`, `Bash(printenv)`, `Bash(printenv *)`, `Bash(*/printenv*)`, `Bash(env)`, `Bash(env *)`, `Bash(export)`, `Bash(export -p*)`, `Bash(set)`, `Bash(declare -p*)`, `Bash(declare -x*)`, `Bash(cat *.env*)`) dans `permissions.deny` du fichier `--settings` de toute tuile Claude : celui des hooks (fusionné avec les réglages d'une tâche par `merge_settings`), ou, sans API locale ni CLI `termf`, `<données>/claude-deny.json` (`write_deny_settings`) ; et en `--disallowedTools` des sessions headless.

## 5. Méthode de travail (à reprendre telle quelle)

- **Une tranche = un sous-agent** dans un worktree isolé, sur une branche `phaseN/<sujet>`, qui ouvre une PR et **ne merge jamais**. Brief autonome : sections du plan à lire, périmètre, fichiers partagés à toucher a minima, tests attendus, vérifications, livrable.
- **Revue** : `/code-review high <PR>` (medium pour de l'UI pure). Les constats repartent à l'agent auteur (il a le contexte), puis nouvelle CI.
