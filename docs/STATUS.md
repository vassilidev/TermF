### Contrats des commandes SSH pour l'interface

`ssh_inventory` → `{dir, keys, agent, hosts, repos, problems}` ; `ssh_generate {name, kind: "ed25519"|"ecdsa"|"rsa", comment, passphrase?}` → chemin ; `ssh_agent_add {path, passphrase?}` ; `ssh_agent_remove {path}` ; `ssh_github_upload {path, title}` ; `ssh_host_preview {host}` → `{diff, warnings}` ; `ssh_host_save {host}` ; `ssh_assign {repo, path?}` ; `ssh_test {host, path?}` → `{ok, message}` (avec `path`, seulement cette clé : `-i … -o IdentitiesOnly=yes`) ; `ssh_fix_permissions` ; `ssh_rotate {path, name, kind, comment, passphrase?, upload}` → `{key, uploaded, hosts, repos, warning, errors}` ; `ssh_trash {path}`. `HostEntry = {alias, hostName?, user?, port?, identityFile?, identitiesOnly?}`. Détails des types : `app/src-tauri/src/ssh.rs`.

### Contrats des commandes de clés (tous formats) pour l'interface

`keys_generate {algorithm, spec}` → `Generated` ; `keys_convert {path, passphrase?, spec}` → `Generated` (commentaire vide : celui de la clé lue) ; `keys_pick_file` → chemin ou `null` (dialogue natif ouvert par le backend) ; `keys_convert`, `keys_reveal` et `keys_test` (y compris son `public`) ne lisent que dans `~/.ssh` (lien qui en sort refusé), les fichiers écrits par TermF et ceux choisis avec `keys_pick_file` pendant la session, le reste est refusé ; `keys_reveal {path, passphrase?}` → la clé privée en clair, seulement sur clic explicite (le fichier tel quel, ou déchiffré avec `passphrase` et réécrit dans son propre format ; une clé en clair que TermF ne sait pas lire, DSA ou `-sk`, est rendue telle quelle) ; `keys_test {path, passphrase?, public?}` → `[Check]` (sans `public`, la clé publique d'à côté : `id.pub`, `api.prod.pub.pem` pour `api.prod.pem`, `k.pub.jwk.json`, `id.pub` pour `id.ppk`…) ; `keys_clipboard_clear {digest}` → `bool` (vide le presse-papiers s'il contient encore le texte dont `digest` est le SHA-256 hexadécimal, sans `\r` et fin rognée : `pbpaste`/`pbcopy`, PowerShell/`clip`, `wl-clipboard`/`xclip`/`xsel` ; erreur s'il n'y a aucun de ces outils). `algorithm = "ed25519"|"p256"|"p384"|"p521"|"rsa2048"|"rsa3072"|"rsa4096"|"x25519"` ; `Spec = {usage: "ssh"|"sign"|"encrypt"|"tls", format: "openssh"|"ppk"|"jwk"|"jwks"|"pkcs8"|"sec1"|"pkcs1"|"spki", name, comment, passphrase?, dir?}` : `usage: "ssh"` avec `openssh` écrit `~/.ssh/<name>` et `.pub` ; tout le reste va dans `dir` (absolu, choisi par l'utilisateur) ou n'est écrit nulle part sans `dir` ; jamais d'écrasement, tout ou rien ; phrase de passe seulement pour `openssh`, `pkcs8` (PBES2, PBKDF2-SHA256 600 000 tours, AES-256-CBC) et `ppk` (version 3, Argon2id) ; `usage` fixe `use` / `alg` d'une JWK (`sign` : EdDSA, ES256/384/512, RS256 ; `encrypt` : ECDH-ES, RSA-OAEP-256). `Generated = {algorithm, fingerprint?, kid, files: [{name, path?, secret, text?}]}` (`kid` : empreinte RFC 7638 ; `text` d'un fichier privé seulement s'il n'a pas été écrit). `Check = {kind: "read"|"passphrase"|"pair"|"signature"|"agreement", ok, detail?, error?}`. Formats lus : OpenSSH, PEM PKCS#1 / SEC1 / PKCS#8 (chiffré compris), SPKI, JWK et JWKS, PuTTY versions 2 et 3. Détails : `crates/termf-ssh/src/{keys,formats,ppk}.rs`.

### Contrats des commandes de synchro pour l'interface

`sync_status` → `Status` ; `sync_probe {remote}` → `bool` (vrai : le remote contient déjà une synchro, l'activer la rejoint avec son mot de passe, sans nouvelle clé de récupération) ; `sync_setup {remote, password, scopes, deviceName?}` → `{recoveryKey?, report, error?}` ; `sync_unlock {password}` ; `sync_recover {recoveryKey, password}` → nouvelle clé de récupération ; `sync_push` et `sync_pull` → `Report` ; `sync_resolve {path, resolution}` → `Report` ; `sync_devices` → `[{id, name, os, lastSync, current}]` ; `sync_change_password {current, password}` → nouvelle clé de récupération ; `sync_scopes {scopes}` → `Status` ; `sync_disable`. Événement `sync-status` (`Status`) après chaque synchro de fond.
`Status = {enabled, remote?, scopes, deviceId?, deviceName?, unlocked, remembered, lastSync?, lastError?, conflicts, missingRepos}` ; `remote = {kind: "git", url} | {kind: "folder", path}` ; `Scope = "config"|"projects"|"conventions"` (`"vault"`, `"sshKeys"` refusés pour l'instant) ; `Report = {pulled, pushed, conflicts, missingRepos, skipped}` ; `skipped = [{path, error}]` (fichier illisible, TOML invalide : ni envoyé ni reçu jusqu'à correction, aussi dans `lastError`) ; `Conflict = {path, keys, local?, remote?}` ; `resolution = {keep: "local"|"remote"} | {keep: "merged", text}` ; `MissingRepo = {project, path, remote?}` ; dates en secondes Unix. `unlocked: false` : demander le mot de passe (`sync_unlock`). Détails : `app/src-tauri/src/sync.rs`, `crates/termf-sync`.

### Contrats des commandes de tickets pour l'interface

`tickets_inbox {project?, refresh?}` → `Inbox = {tickets: [TicketSummary], errors: [{source, message}]}` (sans `project` : issues GitHub ouvertes qui te sont assignées sur tout GitHub ; avec `project` : ce que listent ses sources, fusionné, un ticket listé par deux sources (même URL, fragment ignoré) une seule fois, celui de la première source dans l'ordre Projects → Issues → Jira → MCP ; toutes les pages, le plus récent d'abord ; `refresh` relance les sources MCP au lieu de relire leur dernière réponse ; une source en échec est dans `errors` avec son id et son message, les autres donnent quand même leurs tickets) ; `tickets_configured {project?}` → `[{project, configured, sources}]` (lit la config et les remotes des dépôts, rien sur le réseau : `configured` faux = aucune source utilisable, inbox vide ; GitHub Issues ne compte que si le projet a un dépôt GitHub ; `sources` : ids ci-dessous) ; `tickets_resolve {input, project?}` → `Resolution` (`input` : URL d'issue, `owner/repo#42`, `<dépôt>#42`, `#42`, URL Jira ou clé `ACME-123`, URL ou clé d'un ticket listé par une source MCP ; une copie MCP d'un ticket GitHub ou Jira va à la source native) ; `tickets_run {input, project?, repo?, cols?, rows?}` → `Run` (résout, lit le ticket, crée worktree et branche, ouvre la session Claude Code et émet `session-opened` ; `repo`, nom ou chemin, est requis quand `Resolution.repo` est vide) ; `tickets_runs` → `[Run]` (le plus récent d'abord) ; `tickets_events {id}` → `[RunEvent]` ; `tickets_deliver_preview {id}` → `DeliveryPreview` (ce que la livraison enverrait, à montrer avant) ; `tickets_deliver {id, confirm}` → `Delivery` (la gate humaine, avec le `fingerprint` de l'aperçu validé : commit de exactement ce que l'aperçu listait, push, PR ; refusé si le worktree a changé depuis l'aperçu ou s'il n'est plus sur la branche du run ; relivrer pousse ce qui a changé et retente le commentaire du ticket) ; `tickets_close {id, force?}` → `Run` (refusé s'il reste du travail non poussé, sauf `force`, qui garde alors la branche ; arrête la session du run avant de retirer le worktree ; l'erreur est un objet `CloseError = {kind: "uncommitted"|"unpushed"|"error", message, uncommitted, commits}` : `uncommitted` = des changements non commités, `unpushed` = seulement des commits non poussés (`commits`), `error` = autre chose) ; `open_url {url}` ouvre une adresse `http(s)` dans le navigateur du système (`open`, `xdg-open`, `explorer` ; aucun shell ; refusé : autre schéma, espaces, guillemets, caractères de contrôle). Événement `run-updated` (`Run`) à chaque changement d'un run.
`TicketRef = {provider: "github"|"jira"|"mcp:<source>", key, url}` ; `TicketSummary = {provider, key, url, title, state, labels, assignees, updated, project?, source}` (`state` : l'état du tracker, ou la colonne Status pour un élément de GitHub Projects ; `assignees` : logins GitHub ou noms affichés ; `updated` : ISO 8601 en UTC ; `source` : `github` (Issues), `githubProject`, `jira` ou `mcp:<nom>`) ; `Resolution = {ticket: TicketRef, project, repos: [{name, path}], repo?}` ; `Run = {id, project, ticket: TicketRef, title, repo, worktree?, branch?, base?, status: "running"|"delivered"|"closed"|"failed", prUrl?, created, updated, sessionId?}` (`sessionId` : la session du terminal du run tant qu'elle existe, pour ce lancement de l'app seulement) ; `DeliveryPreview = {files: [{path, change: "added"|"modified"|"deleted"|"renamed", from?}], commits: [{commit, subject}], fingerprint}` (`commits` : déjà faits, pas encore poussés) ; `Delivery = {run: Run, warning?}` (`warning` : échec après l'ouverture de la PR, comme le commentaire du ticket) ; `RunEvent = {id, run, at, kind, …}` avec `kind` : `worktree_created {path, branch, base}`, `session_opened {session}`, `committed {commit, message}`, `pushed {branch, commit}`, `pr_opened {url}`, `ticket_commented {url}`, `ticket_moved {to}`, `closed {dropped}`, `failed {error}` ; dates en secondes Unix. Seuls les dépôts sur github.com (alias SSH compris) sont reconnus. Détails : `app/src-tauri/src/tickets.rs`, `crates/termf-tickets`.

### Contrats de la reprise des runs, du nettoyage après merge et de l'inbox économique (suites de la phase 3)

Reprise : `tickets_resume {id, cols?, rows?}` → `{run: Run, warning?}` (ouvre une nouvelle session dans le worktree du run avec `claude --resume <conversation>`, le même environnement que la première : ports et variables de la dernière préparation, sans la relancer, garde-fou `termf guard`, `--disallowedTools`, `--add-dir` du brief, bibliothèque du projet ; émet `session-opened` puis `run-updated`) ; refusée si le run n'est ni `running` ni `delivered`, si son worktree a disparu, s'il a été lancé avant cette version (pas de conversation connue), si une reprise du même run est en cours ou si une session de TermF tourne encore dans cette conversation (celle du run, ou une tuile dont les hooks donnent ce `session_id`) : jamais deux processus sur une conversation. Que Claude Code ait encore la conversation n'est qu'un indice (le `$CLAUDE_CONFIG_DIR` du shell de l'agent peut différer de celui de TermF lancé depuis le Dock) : sans `<dossier Claude>/projects/*/<conversation>.jsonl`, la reprise part quand même avec un `warning` (« may no longer have the conversation »), et c'est la session elle-même qui dit si la conversation n'existe plus. Au lancement, TermF génère l'UUID et le passe par `--session-id` ; à chaque `SessionStart` d'une session de run, la conversation enregistrée suit (`/clear` en ouvre une nouvelle, la remise à zéro du contexte aussi). CLI : `termf run resume <run>` (par l'app, comme `termf run` ; le `warning` sur la sortie d'erreur ; ni `--project` ni `--repo`). Le garde-fou refusait déjà `termf run …` dans la session d'un run.
Nettoyage après merge : `tickets_check` → `PrCheck = {cleanups: [Cleanup], errors: [{run, message}]}` (à appeler à l'ouverture de la vue Tickets : demande à GitHub l'état de la PR de chaque run `delivered` dont le sort n'est pas encore connu, par `GET repos/<owner>/<name>/pulls/<n>` avec ETag ; l'app le fait aussi 30 s après le démarrage puis toutes les 15 min ; sans run livré à PR ouverte, rien ne part sur le réseau ; `cleanup = "off"` : rien du tout ; `errors` : les runs dont GitHub n'a pas pu dire l'état de la PR, redemandés la fois suivante, aussi écrits dans le journal de l'app pour la vérification de fond) ; `tickets_cleanup {id}` → `Run` ou `CloseError` comme `tickets_close` sans `force` (refusé tant que la PR est ouverte (une PR connue fermée est redemandée, elle a pu être rouverte : son état est alors oublié), qu'il reste du travail non commité ou des commits non poussés ; arrête la session, teardown de la préparation (copie de base, ports), retire le worktree et la branche locale ; marche quel que soit `cleanup`, c'est l'action explicite). Événement `run-cleanup` (`Cleanup`) pour chaque PR trouvée mergée ou fermée, une seule fois, avec `run-updated` ; l'interface en fait la notification (rien côté backend, les textes restent dans `i18n.ts`). `Cleanup = {run: Run, cleaned, error?}` (`cleaned` : TermF a fermé le run ; sinon il attend `tickets_cleanup`, et `error` dit pourquoi TermF n'a pas pu, par exemple du travail non commité en mode `auto`). Config : `[tickets] cleanup = "auto"|"ask"|"off"` dans `termf.toml` (défaut `ask` : la PR mergée est signalée, la clôture reste à l'utilisateur ; `auto` : TermF ferme le run si rien ne serait perdu, une seule tentative).
`Run` gagne `claudeSession?` (la conversation Claude Code que la reprise prendra ; absent pour un run d'avant cette version, qui ne se reprend pas) et `prState?: "merged"|"closed"` (connu une fois la PR mergée ou fermée : le run est alors « prêt à nettoyer » tant qu'il est `delivered` ; oublié à chaque nouvelle livraison, qui le fait redemander). `RunEvent` gagne `session_resumed {session, conversation}`, `pr_merged {url}`, `pr_closed {url}`. Base : colonnes `claude_session` et `pr_state` ajoutées à `runs` à l'ouverture (`user_version = 3`), écrites seulement par des mises à jour ciblées (jamais par la réécriture d'une copie du run, pour qu'une livraison ou une fermeture en cours ne défasse ni un `/clear` ni un merge) ; `pr_state` et l'événement `pr_merged`/`pr_closed` dans une même transaction, seulement si le run est encore `delivered` et que l'état n'est pas déjà connu (deux vérifications simultanées l'enregistrent une fois). Dans l'app, vérification et `tickets_cleanup` passent l'une après l'autre. La dernière préparation garde aussi son environnement dans `<dossier git du worktree>/termf-setup.json` (`env`).
Inbox : GitHub Issues (avec ou sans projet) lit chaque page de `search/issues` (100 par page, au plus 10) par `gh api --include` avec l'ETag de la dernière réponse (`If-None-Match`) ; un 304, qui ne coûte rien sur le quota, rend la réponse gardée. Cache en mémoire par requête et par page dans l'app (le `Tickets` partagé ; la CLI repart de zéro à chaque commande), 256 requêtes au plus. `refresh: true` demande sans ETag (relecture complète) et relance toujours les sources MCP ; sans `refresh`, les sources MCP répondent de leur cache comme avant. GitHub Projects v2 reste lu par `gh api graphql`, que GitHub ne sert pas en requêtes conditionnelles (choix validé : pas de passage à l'API REST des Projects) ; Jira et MCP inchangés.

### Contrats des sources de tickets (section « Tickets » de l'éditeur de projet)

`tickets_sources {project}` → `Sources = {trackers: Trackers, jiraToken, githubRepos, mcpTools}` (`jiraToken` : le trousseau a un jeton pour le site et l'e-mail de `jira` ; `githubRepos` : `owner/name` des dépôts GitHub du projet, ceux que lit GitHub Issues ; `mcpTools` : par source MCP, les outils de lecture que TermF connaît pour son serveur) ; `tickets_sources_save {project, trackers}` → `Sources` (écrit `[trackers]` du projet en gardant commentaires et clés inconnues, sans écrire les valeurs par défaut ; aucune source = un `[trackers]` vide ; oublie la dernière réponse des seules sources MCP dont les réglages ont changé ; refuse un tableau, un site, un e-mail, un nom d'outil ou de source invalide ; l'éditeur ne l'appelle que si les sources ont changé) ; `tickets_source_test {project, trackers, source}` → au plus 5 `TicketSummary` (`trackers` tel que l'éditeur le tient, enregistré ou non ; rien n'est mis en cache) ; `tickets_jira_token {site, email}` → `bool`, `tickets_jira_token_save {site, email, token}` et `tickets_jira_token_forget {site, email}` (trousseau du système, service `dev.termf.tickets`, compte `jira:<site>:<email>`, jamais dans la config, la base ni les erreurs) ; `tickets_mcp_servers {project?}` → `[{name, status, tools}]` (`claude mcp list` depuis le premier dépôt du projet, lent : il vérifie chaque serveur ; `status` tel que Claude Code l'écrit ; `tools` : outils de lecture connus, vide = à lister).
`Trackers = {github?: {repo?, comment, issues, project?, columns, mine, transition?}, jira?: {site, email, jql?, project?, comment, transition?}, mcp: {<nom>: {server, tools, prompt?}}, implicit}`, les mêmes clés dans le TOML du projet (sauf `implicit`, en lecture seule : le projet n'a pas de `[trackers]` et lit donc, comme avant les sources, GitHub Issues sur les remotes GitHub de ses dépôts ; enregistrer les sources les écrit) :
- `[trackers.github]` : GitHub Issues (issues ouvertes assignées dans les dépôts du projet et `repo` ; `issues` vrai par défaut sauf si `project` est indiqué ; sans dépôt GitHub, la source est ignorée) et, avec `project = "owner/numéro"` (ou l'URL du tableau), GitHub Projects v2 via `gh api graphql` : issues ouvertes du tableau, non archivées, dans `columns` (valeurs du champ Status, toutes si vide), assignées à toi si `mine` (vrai par défaut) ; `transition = "<Status>"` déplace l'issue sur le tableau à la livraison (rien par défaut ; `gh auth refresh -s project` peut être nécessaire).
- `[trackers.jira]` : Jira Cloud, API REST v3 par `curl` (aucune pile HTTP/TLS ajoutée ; jeton passé sur l'entrée standard de curl, `--disable` ignore `~/.curlrc`) ; `site`, `email`, `jql` (défaut `assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC`, pagination `nextPageToken` de `/rest/api/3/search/jql`), `project` (préfixe de clé accepté pour une clé collée seule ; sans lui, toute clé va au projet), `comment` (lien distant vers la PR à la livraison) et `transition` (statut ou transition à la livraison), tous deux désactivés par défaut. Description et commentaires ADF convertis en Markdown.
- `[trackers.mcp.<nom>]` : `server` (nom dans `claude mcp list`), `tools` (noms courts, sans motif ; vide = outils de lecture connus pour Atlassian, GitHub, Linear), `prompt` (quoi chercher, facultatif). Lecture par `claude -p --output-format json --json-schema <schéma> --model haiku --max-budget-usd 0.25 --tools "" --allowedTools mcp__<serveur>__<outil>,… --permission-mode dontAsk --permission-prompts none --restricted --settings '{"disableAllHooks":true}' --disable-slash-commands --no-session-persistence` depuis le premier dépôt du projet : aucun outil intégré, seuls les outils listés, tout le reste refusé sans personne pour l'accepter, ni réglages (donc ni règles `allow`) de l'utilisateur ou du dépôt, ni hooks, skills ou commandes. Réponse revalidée (schéma strict, clé, URL `http(s)` sans espace ni guillemet, tailles) puis refusée en bloc au moindre écart ; mise en cache dans `termf.db` (table `listed`) jusqu'au prochain `refresh` ; le ticket lu pour un run est encadré comme donnée comme les autres. Une source MCP est en lecture seule : ni commentaire, ni transition, ni lien.
À la livraison, les écritures permises sur le ticket (`comment`, puis `transition`) sont tentées une fois chacune ; un échec devient un `warning` retenté à la livraison suivante.

Chaque minute, l'app réécrit les entrées périmées (tâche changée ailleurs, app déplacée) et retire celles des tâches supprimées, passées en tuile ou sur une autre machine ; une tâche launchd en cours n'est pas déchargée (mise à jour reportée), le rechargement attend que l'ancienne soit partie. CLI : `termf schedule list | add | edit | rm | run [--scheduled] | history [--run <n>] | install | uninstall` (`--machine <nom>|any`). ### Contrats des commandes CI/CD pour l'interface

GitHub Actions seulement, via le `gh` du système ; `repo` est le chemin d'un dépôt, lu par son premier remote GitHub (refusé sinon : « has no GitHub remote »), ou `owner/name` tel que GitHub le donne (le `repo` d'un `WorkflowRun`, utile quand la PR n'est pas sur le premier remote). `ci_runs {repo, branch?, status?, pr?, page?}` → `RunPage` (30 par page, la plus récente d'abord ; `pr` : exécutions sur le dernier commit de la PR, `branch` ignorée alors ; `status` : `queued`, `in_progress`, `success`, `failure`, `cancelled`… de l'API GitHub) ; `ci_run {repo, id}` → `RunDetail` (jobs de la dernière tentative, toutes les pages) ; `ci_log {repo, job}` → `JobLog` (téléchargé à chaque appel ; refusé tant que le job tourne) ; `ci_rerun {repo, id, failed}` (`failed` : seulement les jobs en échec) ; `ci_cancel {repo, id}` ; `ci_workflows {repo}` → `[Workflow]` ; `ci_inputs {repo, path, gitRef?}` → `[Input]` (lues dans le fichier du workflow à `gitRef`, sinon la branche par défaut ; refusé sans déclencheur `workflow_dispatch`) ; `ci_dispatch {repo, workflow, gitRef?, inputs}` (`workflow` : id ou nom de fichier, `inputs` : `{nom: valeur}` en texte) ; `ci_checks {run}` → `[WorkflowRun]` (les exécutions du dernier commit de la PR d'un run de ticket ; refusé sans PR) ; `ci_failure {run, job}` → `AgentMessage` (écrit `<data>/runs/<run>/brief/ci-<job>.md` : workflow, job, étape en échec, journal autour de la première et de la dernière erreur — 30 lignes avant, 5 après —, sinon ses 150 dernières lignes, encadré comme donnée non fiable dans `<ci-failure>`) ; `ci_send {session, text}` (tape `text` puis Entrée dans la session, comme `termf say`) ; `ci_poll` (l'interface l'appelle chaque minute : redemande les exécutions suivies) ; `ci_notify` → `"mine"|"all"|"off"` ; `ci_notify_set {notify}`. ### Contrats du runtime d'agents headless (ARCHITECTURE §6, pour la vue conversation)

`agent_start {spec, prompt?}` → `AgentSession` (crée la session et démarre son processus ; `prompt` : son premier message) ; `agent_send {id, text}` (entre deux tours seulement ; une session sans processus — arrêtée, en erreur, après un redémarrage de l'app — reprend d'abord sa conversation avec `--resume` ; refusé pendant un tour, en main dans une tuile ou budget épuisé) ; `agent_interrupt {id}` (pendant un tour : il finit en `interrupted`, la conversation continue) ; `agent_answer {id, request, allow, message?}` (répond à une demande de permission ; `message` : la raison du refus, transmise à l'agent) ; `agent_stop {id}` → `AgentSession` (interrompt le tour en cours, ferme l'entrée standard, tue le groupe de processus au bout de 10 s) ; `agent_takeover {id, cols?, rows?}` → `SessionSummary` (« prendre la main », entre deux tours seulement : arrête le processus headless et attend sa fin, puis ouvre une tuile normale `claude --resume <sessionId>` avec le modèle, l'effort et le mode de permission de la session, plugin et bibliothèque comme toute tuile, et émet `session-opened` ; jusqu'à ce que la tuile soit ouverte, envoyer, arrêter, reprendre ou rendre la main sont refusés ; refusé tant que l'agent n'a reçu aucun message, et budget épuisé, une tuile n'ayant pas de plafond) ; `agent_handback {id}` → `AgentSession` (« rendre la main » : termine le processus de la tuile, qui reste affichée comme terminée, attend sa fin — 10 s au plus, sinon erreur et la session reste dans la tuile —, puis reprend en headless avec `--resume`) ; `agent_sessions` → `[AgentSession]` (la plus récente d'abord) ; `agent_events {id, after?}` → `[StoredEvent]` (ceux dont l'id dépasse `after`). Événements `agent-event` (`StoredEvent`) à chaque événement et `agent-updated` (`AgentSession`) à chaque changement d'une session.
`SessionSpec = {cwd, title, project?, agent?, model?, effort?, permissionMode?, budget?}` (`cwd` absolu ; `title` : le nom du dossier par défaut ; `project` : celui dont la bibliothèque s'applique, par défaut celui qui liste le dossier ; `agent` : l'entrée de `[agents]`, qui doit lancer Claude Code, par défaut la première qui le fait ; une valeur vide = le défaut de Claude Code, refusée si elle commence par `-` ; `budget` en USD pour toute la session, tous processus confondus) ; `AgentSession = SessionSpec & {id, runtime: "claude-code", sessionId, state, cost, context?: Gauge, tile?, created, updated}` (`sessionId` : l'id de la conversation Claude Code, choisi par TermF (`--session-id`) ; `cost` : cumul des processus headless, pas ce que dépense une tuile ; `context` : la jauge après le dernier tour, même type que celle des tuiles ; `tile` : la tuile d'une session prise en main, pour ce lancement de l'app) ; `state` : `working` (un tour en cours), `waiting` (une permission attend sa réponse), `idle` (attend le message suivant), `interactive` (en main dans une tuile), `stopped` (pas de processus : le message suivant reprend), `error` (le dernier tour ou le processus a échoué : le message suivant reprend), `budget` (budget épuisé) ; `StoredEvent = {id, session, at, kind, …}` (`id` 0 : texte au fil de l'eau, jamais stocké), `kind` : `started {resumed}`, `init {sessionId, model, permissionMode}` (une fois par processus), `user {text}`, `delta {text}` (texte partiel, envoyé à l'UI seulement ; le `text` suivant le contient en entier), `text {text, parent?}`, `tool_use {id, name, input, parent?}`, `tool_result {id, output, isError, truncated, parent?}` (`output` coupé à 4 000 caractères ; `parent` : l'appel d'outil du sous-agent qui parle, absent pour l'agent lui-même, pour les imbriquer), `permission {request, tool, input, description?}`, `permission_answer {request, allow, message?}`, `denied {tool, message}` (refusé par le mode de permission, sans question), `turn_end {outcome: "done"|"interrupted"|"error"|"budget", result?, error?, usage: {input, output, cacheRead, cacheCreation}, cost, total, context?}` (`cost` : ce tour, `total` : la session jusque-là, en USD), `error {message}` (processus mort pendant un tour : la fin de son stderr), `exited {code?}`, `taken_over {tile}`, `handed_back` ; dates en secondes Unix.
Exécution : `<commande de l'agent> -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio --session-id|--resume <id> [--model] [--effort] [--permission-mode] [--max-budget-usd <reste du budget>] [--plugin-dir <bibliothèque>] [--append-system-prompt-file <prompt>]` par le shell de connexion, dans `cwd`, dans son propre groupe de processus ; messages, interruption (`control_request` `interrupt`) et réponses de permission (`control_response` : `allow` + `updatedInput`, ou `deny` + `message`) sur stdin. Vérifié avec Claude Code 2.1.330 (essai réel `cargo test -p termf-agents -- --ignored real_claude`, Haiku, quelques centimes) : `--permission-prompt-tool stdio`, absent de `--help`, est ce qu'utilise l'Agent SDK ; `system/init` revient à chaque tour ; `total_cost_usd` cumule le processus, donc un tour coûte la différence ; un tour interrompu finit en `error_during_execution` avec `terminal_reason: aborted_*`, un budget dépassé en `error_max_budget_usd`. Jauge : jetons en contexte de la dernière réponse (`input + cache_creation + cache_read`) sur `modelUsage.<modèle>.contextWindow`. Une conversation n'a jamais deux processus : la prise en main attend la fin du processus headless avant d'ouvrir la tuile, la remise attend la fin de la tuile avant de relancer. Le pid du groupe de processus est gardé en base tant qu'il tourne ; quitter l'app tue les processus headless ; au démarrage, un processus laissé par le lancement précédent, reconnu à sa ligne de commande qui contient l'id de la conversation (`ps`, PowerShell sous Windows ; un pid réattribué à un autre programme n'est jamais touché), est tué, et les sessions restées vivantes passent à `stopped` ; aucun processus ne démarre pour une conversation dont un processus tourne encore. Un événement qui ne peut pas être enregistré est perdu, jamais l'état, le coût ou la jauge qui l'accompagnent. Lignes inconnues ou non JSON ignorées. Données : `<data>/termf.db` (tables `agent_sessions`, `agent_events`), `<data>/agents/<id>/events.jsonl`, plugin et prompt de la bibliothèque dans `<data>/agents/<id>/session/` (réécrits à chaque processus). CLI : `termf agent ls | start [--prompt <texte|->] [--dir] [--title] [--project] [--agent] [--model] [--effort] [--permission-mode] [--budget] | send <id> <texte> | events <id> [--after <n>] | interrupt <id> | allow|deny <id> <requête> [<message>] | stop <id> | takeover <id> | handback <id>` (`ls` et `events` lisent la base, sans l'app). Détails : `crates/termf-agents`, `app/src-tauri/src/agents.rs`.

## 4. Dettes et points non vérifiés connus

- **Jamais testé à la main dans la vraie fenêtre** : l'interface a été vérifiée dans Chrome avec un IPC simulé, l'app réelle au démarrage et via la CLI. Windows et Linux : compilés et testés en CI, jamais lancés.
- Raccourcis : `` Ctrl+` `` sur clavier AZERTY non vérifié ; sous Linux/Windows, `Ctrl+K` / `Ctrl+J` dans un terminal vont au shell (il faut `Shift`).
- Statut : après Échap, retour à « inactif » seulement via `idle_prompt` (~60 s) ; `termf ls` liste aussi le terminal rapide.
- Fichiers : `Cmd+Q` ne protège pas les onglets non enregistrés ; un outil défini seulement dans `.zshrc` n'est pas trouvé pour `gh` / l'éditeur externe (PATH de connexion sans `-i`).
- Bibliothèque : règles livrées en français et le reste en anglais ; « promouvoir / dériver » non fait ; surcharges par lancement non branchées sur `pty_spawn` ; `applies_to` ne filtre pas encore (pas de rôle en session manuelle), donc un ajustement de rôle issu d'une convention atteint toutes les sessions ; archive `tar.gz` sans signature ni `--with-secrets`.
- Conventions : mesure d'impact seulement sur macOS (`sandbox-exec`), « non mesuré » ailleurs ; hooks en `/bin/sh` (pas sous Windows) ; une archive importée qui contient à la fois le `pack.toml` d'un projet et la règle-hook l'enregistrerait (il faudrait un registre de confiance hors config) ; dialogues natifs jamais ouverts à la main ; jamais lancé avec opus sur un gros projet ni avec une réponse « questions » réelle.
- Veille : jamais lancée avec un vrai Claude Code (faux binaire seulement) ; pas d'annulation d'un lancement ; revue seulement dans l'app (la CLI lance et affiche) ; l'agent peut encore faire sortir le texte des éléments dans une URL (consigne contraire, pas de garantie).
- SSH : `key()` lit la `.pub` d'une clé privée à travers un lien qui sort de `~/.ssh`, alors que `scan()` écarte ce même fichier ; clés matérielles `-sk`, GitLab, ACL Windows, askpass sous Windows non faits ou non vérifiés ; avis RUSTSEC-2023-0071 sur `rsa` (déchiffrement RSA non utilisé ; une signature RSA seulement pour le test local d'une clé). Clés tous formats : jamais essayées dans la vraie fenêtre ; vidage du presse-papiers non vérifié sous Windows et Linux (sous Linux il faut wl-clipboard, xclip ou xsel, sinon c'est dit) ; PEM « traditionnel » chiffré (`DEK-Info`) refusé avec un message ; pas de CSR ni de certificat pour l'usage TLS ; ssh-key 0.6.7 passe `p` deux fois en convertissant une clé RSA, d'où la conversion et la signature RSA par la crate `rsa`.

## 5. Méthode de travail (à reprendre telle quelle)

- **Une tranche = un sous-agent** dans un worktree isolé, sur une branche `phaseN/<sujet>`, qui ouvre une PR et **ne merge jamais**. Brief autonome : sections du plan à lire, périmètre, fichiers partagés à toucher a minima, tests attendus, vérifications, livrable.
- **Revue** : `/code-review high <PR>` (medium pour de l'UI pure). Les constats repartent à l'agent auteur (il a le contexte), puis nouvelle CI.
- **Merge** : seulement si les 3 CI (macOS, Ubuntu, Windows) sont `SUCCESS` ; si `main` a bougé, `gh pr update-branch <PR> --rebase` puis CI à nouveau ; merge en squash, branche supprimée, worktree retiré.
- **Interface** : toute modification visible a sa page de captures avant/après (Chrome + IPC simulé, clair et sombre). Depuis le 2026-11-21, le propriétaire autorise le **merge automatique** après revue + CI 3 OS et fera **une revue groupée à la fin** : chaque page est copiée dans `.claude/reviews/<pr>-<sujet>.html` (exclu de git localement), à lui présenter ensemble en fin de travail. **Revue groupée en mode « swipe »** (demande du propriétaire, ARCHITECTURE §8.2) : artifact privé https://claude.ai/artifact/DJWDnJvH7KWSpP64od6veR ; réponses dans sa base, collection `decisions`, un document par carte `pr<N>-<écran>` (`decision: approve|reject|change|skip`, `comment`, `pins`) — les lire avec `ArtifactData list`. Générateur dans `.claude/reviews/tools/` (`manifest.json` : une ligne par PR, avec `only` = **2 à 4 écrans essentiels maximum** (le propriétaire ne peut pas tout revoir ; jamais les états vide/chargement/erreur) ; `build_deck.py` ; republier sur la même URL, voir `README.md`), captures durables dans `.claude/reviews/shots/<tranche>/`. Après chaque PR d'UI : copier ses captures dans `shots/`, l'ajouter au manifeste, reconstruire et republier. Pages HTML individuelles aussi gardées : `pr10-ssh-ui.html`, `pr11-sync-ui.html`, `pr13-context-reset.html`, `pr14-tickets-ui.html`. Laissé de côté par ces UI faute de commande Rust : retirer de l'agent une clé sans fichier, tester un dépôt avec son `core.sshCommand`, GitLab, clés `-sk`, cloner un dépôt manquant, oublier un appareil, `skipped` dans `Status` ; erreurs du backend en anglais.
- **Au plus 4 agents en parallèle** : le 2026-11-21, un kernel panic APFS (bug de macOS sous forte lecture parallèle de dossiers) a coupé la machine pendant que 8 agents compilaient ; garder la charge disque modérée.
- **Disque limité** : `cargo clean` dans chaque worktree terminé ; profil dev allégé ; pas de build release inutile.
- **Commits** terminés par les lignes `Co-Authored-By` et `Claude-Session` ; les règles de `CLAUDE.md` s'appliquent à tous (périmètre strict, demander en cas de doute, aucun texte modifié sans demande, rien de propre à une machine).
- Les secrets, le vrai `~/.ssh`, le vrai agent SSH et la vraie config ne sont **jamais** utilisés dans les tests : `HOME` et `SSH_AUTH_SOCK` pointent vers des dossiers jetables.
