### Contrats de la reprise des runs, du nettoyage après merge et de l'inbox économique (suites de la phase 3)

Reprise : `tickets_resume {id, cols?, rows?}` → `{run: Run, warning?}` (ouvre une nouvelle session dans le worktree du run avec `claude --resume <conversation>`, le même environnement que la première : ports et variables de la dernière préparation, sans la relancer, garde-fou `termf guard`, `--disallowedTools`, `--add-dir` du brief, bibliothèque du projet ; émet `session-opened` puis `run-updated`) ; refusée si le run n'est ni `running` ni `delivered`, si son worktree a disparu, s'il a été lancé avant cette version (pas de conversation connue), si une reprise du même run est en cours ou si une session de TermF tourne encore dans cette conversation (celle du run, ou une tuile dont les hooks donnent ce `session_id`) : jamais deux processus sur une conversation. Que Claude Code ait encore la conversation n'est qu'un indice (le `$CLAUDE_CONFIG_DIR` du shell de l'agent peut différer de celui de TermF lancé depuis le Dock) : sans `<dossier Claude>/projects/*/<conversation>.jsonl`, la reprise part quand même avec un `warning` (« may no longer have the conversation »), et c'est la session elle-même qui dit si la conversation n'existe plus. Au lancement, TermF génère l'UUID et le passe par `--session-id` ; à chaque `SessionStart` d'une session de run, la conversation enregistrée suit (`/clear` en ouvre une nouvelle, la remise à zéro du contexte aussi). CLI : `termf run resume <run>` (par l'app, comme `termf run` ; le `warning` sur la sortie d'erreur ; ni `--project` ni `--repo`). Le garde-fou refusait déjà `termf run …` dans la session d'un run.
Nettoyage après merge : `tickets_check` → `PrCheck = {cleanups: [Cleanup], errors: [{run, message}]}` (à appeler à l'ouverture de la vue Tickets : demande à GitHub l'état de la PR de chaque run `delivered` dont le sort n'est pas encore connu, par `GET repos/<owner>/<name>/pulls/<n>` avec ETag ; l'app le fait aussi 30 s après le démarrage puis toutes les 15 min ; sans run livré à PR ouverte, rien ne part sur le réseau ; `cleanup = "off"` : rien du tout ; `errors` : les runs dont GitHub n'a pas pu dire l'état de la PR, redemandés la fois suivante, aussi écrits dans le journal de l'app pour la vérification de fond) ; `tickets_cleanup {id}` → `Run` ou `CloseError` comme `tickets_close` sans `force` (refusé tant que la PR est ouverte (une PR connue fermée est redemandée, elle a pu être rouverte : son état est alors oublié), qu'il reste du travail non commité ou des commits non poussés ; arrête la session, teardown de la préparation (copie de base, ports), retire le worktree et la branche locale ; marche quel que soit `cleanup`, c'est l'action explicite). Événement `run-cleanup` (`Cleanup`) pour chaque PR trouvée mergée ou fermée, une seule fois, avec `run-updated` ; l'interface en fait la notification (rien côté backend, les textes restent dans `i18n.ts`). `Cleanup = {run: Run, cleaned, error?}` (`cleaned` : TermF a fermé le run ; sinon il attend `tickets_cleanup`, et `error` dit pourquoi TermF n'a pas pu, par exemple du travail non commité en mode `auto`). Config : `[tickets] cleanup = "auto"|"ask"|"off"` dans `termf.toml` (défaut `auto` depuis la passe UX n° 3 : TermF ferme le run d'une PR **mergée** si rien ne serait perdu, une seule tentative, sinon le signale ; une PR fermée sans merge (elle peut être reprise) et un run dont la session est au travail sont seulement signalés, comme avec `ask` : tuile vivante dont l'agent travaille, attend, démarre, ne dit pas son état ou s'est arrêté il y a moins de 30 min, ou run d'équipe `running` ; `after_merge(auto, busy, stop_session)` ; `ask` : la PR mergée ou fermée est signalée, la clôture reste à l'utilisateur).
`Run` gagne `claudeSession?` (la conversation Claude Code que la reprise prendra ; absent pour un run d'avant cette version, qui ne se reprend pas) et `prState?: "merged"|"closed"` (connu une fois la PR mergée ou fermée : le run est alors « prêt à nettoyer » tant qu'il est `delivered` ; oublié à chaque nouvelle livraison, qui le fait redemander). `RunEvent` gagne `session_resumed {session, conversation}`, `pr_merged {url}`, `pr_closed {url}`. Base : colonnes `claude_session` et `pr_state` ajoutées à `runs` à l'ouverture (`user_version = 3`), écrites seulement par des mises à jour ciblées (jamais par la réécriture d'une copie du run, pour qu'une livraison ou une fermeture en cours ne défasse ni un `/clear` ni un merge) ; `pr_state` et l'événement `pr_merged`/`pr_closed` dans une même transaction, seulement si le run est encore `delivered` et que l'état n'est pas déjà connu (deux vérifications simultanées l'enregistrent une fois). Dans l'app, vérification et `tickets_cleanup` passent l'une après l'autre. La dernière préparation garde aussi son environnement dans `<dossier git du worktree>/termf-setup.json` (`env`).
Inbox : GitHub Issues (avec ou sans projet) lit chaque page de `search/issues` (100 par page, au plus 10) par `gh api --include` avec l'ETag de la dernière réponse (`If-None-Match`) ; un 304, qui ne coûte rien sur le quota, rend la réponse gardée. Cache en mémoire par requête et par page dans l'app (le `Tickets` partagé ; la CLI repart de zéro à chaque commande), 256 requêtes au plus. `refresh: true` demande sans ETag (relecture complète) et relance toujours les sources MCP ; sans `refresh`, les sources MCP répondent de leur cache comme avant. GitHub Projects v2 reste lu par `gh api graphql`, que GitHub ne sert pas en requêtes conditionnelles (choix validé : pas de passage à l'API REST des Projects) ; Jira et MCP inchangés.
Interface (vue Tickets) : `tickets_check` à chaque ouverture de la vue ; `watchTickets()` (`tickets.svelte.ts`, lancé par `+page.svelte`) suit `run-updated` et notifie chaque `run-cleanup` (textes `ticketsUi*` de `i18n.ts`) ; la session d'un run est `Run.sessionId` (si elle tourne encore) ; « Reprendre » pour un run `running` ou `delivered` sans session vivante, avec `claudeSession` et un worktree ; « Prêt à nettoyer » = `delivered` avec `prState` ; aide « question de confiance » quand la session du run reste `starting` plus de 6 s (TermF ne répond jamais à cette question). Logique pure testée par `pnpm test` : `lib/tickets-logic.ts` (`liveSession`, `readyToClean`, `resumable`, `refusal`, `cleanupNotice`).

Description et commentaires ADF convertis en Markdown.
- `[trackers.mcp.<nom>]` : `server` (nom dans `claude mcp list`), `tools` (noms courts, sans motif ; vide = outils de lecture connus pour Atlassian, GitHub, Linear), `prompt` (quoi chercher, facultatif). Réponse revalidée (schéma strict, clé, URL `http(s)` sans espace ni guillemet, tailles) puis refusée en bloc au moindre écart ; mise en cache dans `termf.db` (table `listed`) jusqu'au prochain `refresh` ; le ticket lu pour un run est encadré comme donnée comme les autres. Une source MCP est en lecture seule : ni commentaire, ni transition, ni lien.
À la livraison, les écritures permises sur le ticket (`comment`, puis `transition`) sont tentées une fois chacune ; un échec devient un `warning` retenté à la livraison suivante.

`TeamRun = {run, target: {run, project, repo, repoPath, worktree, ticket, title, brief}, workflow, state: "running"|"waiting"|"paused"|"stopped"|"budget"|"done", planOnly, budget?, cost, maxParallel, workflowRules, rules, taskRules: {tâche: {règle: niveau}}, plan?: Plan, uiChanged, steps: [Step], note?, created, updated}` (`waiting` : plus rien ne tourne et une gate ou une étape bloquée t'attend ; `note` : pourquoi) ; `Step = {key, kind: "agent"|"gate"|"foreach"|"shell"|"rules"|"visual"|"connector"|"task", role?, task?, needs, state: "pending"|"running"|"waiting"|"blocked"|"done"|"skipped", plan, over?, run?, prompt?, budget?, session?, sessions, after, attempt, feedback?, worktree?, base?, integrated, files, report?: Report, violations: [Violation], cost, note?, started?, finished?}` (`key` : nom de l'étape du workflow, `<foreach>:<tâche>` pour une tâche ; `waiting` = gate, `blocked` = échec ou question de l'agent ; `note` : pourquoi elle attend, est bloquée ou sautée, ou la sortie d'une commande) ; `Plan` (annexe A, clés en snake_case) `= {summary, acceptance: [{id, text}], out_of_scope, questions, tasks: [{id, role, squad, repo, size: "S"|"M"|"L", covers, goal, files_hint, depends_on, ui_impact}]}` ; `Report` (annexe B) `= {status: "done"|"blocked"|"failed", summary, covers, text_changes: [{file, text, justified_by}], affected_views: [{url, state, viewports}], out_of_scope_findings, questions}` ; `Violation = {rule, file?, message, blocking}` ; `TeamEvent = {id, run, at, step?, kind, message}`, `kind` : `started`, `resumed`, `step_started`, `step_done`, `step_waiting`, `step_blocked`, `step_skipped`, `retry`, `plan`, `violation`, `approved`, `revised`, `rules`, `paused`, `stopped`, `budget`, `done` (puis `routed`, `answered`, `review`) ; dates en secondes Unix.
Workflows : livrés `library/workflows/default.toml` (cadrage PO → plan du chef d'orchestre → gate `approve-plan` → `implement`, une étape par tâche → `checks` → `rules` → `review` (reviewer, voir plus bas) → `security` (secops) et `visual` → `deliver`) et `hotfix.toml` (`extends = "default"`, gate du plan coupée) ; couches livré → global (`<config>/library/workflows/`) → projet → dépôt (`<dépôt>/.termf/workflows/<nom>.toml`, dont TermF retire `run`, `budget_usd` et `[rules]`) ; `extends` fusionne étape par étape (son propre nom : la couche d'en dessous ; un autre nom : ce workflow) ; une étape `enabled = false` est transparente ; choix : `options.workflow`, sinon `[workflows] default` du projet, sinon `default`. Clés d'étape : `type`, `role`, `needs`, `enabled`, `over = "<étape>.tasks"` (l'étape d'agent dont la réponse est le plan), `run` (`{{ repo.checks }}` = `checks` du dépôt dans les `[[repos]]` du projet ; aucune commande = étape sautée), `prompt` (texte ajouté au brief), `budget_usd` (par session ; pour un `foreach`, `step = { budget_usd = … }`), `actions` (lu, pas encore utilisé) ; à la racine `max_parallel_agents` (4), `budget_usd`, `[rules]`.
Déroulé : une session headless neuve par étape d'agent, avec le rôle de l'étape (de la tâche pour une tâche), le titre `<ticket> · <étape> · <rôle>`, `--json-schema` (le plan pour l'étape d'où vient le `foreach`, le rapport sinon), `--disallowedTools Bash(git push:*) Bash(gh pr:*) Bash(termf:*)` et le hook `termf guard` (`guard`, voir la revue de code plus bas), le mode `acceptEdits` si le rôle n'en donne pas, l'effort de la taille de la tâche (S `medium`, M `high`, L `xhigh`, borné par `effort_range` du rôle), un budget = le plus petit entre celui de l'étape et sa part de ce qui reste au run (le reste, moins ce que les sessions en cours peuvent encore dépenser, partagé entre les étapes d'agent prêtes à démarrer, dans la limite des places libres), et un brief de passation : étape, tâche (but, critères, fichiers pressentis), plan (résumé, critères, hors périmètre), résumés des rapports des étapes finies, retour à prendre en compte, puis le ticket encadré comme donnée non fiable. Le plan est revérifié (ids uniques, rôles connus de la bibliothèque, seulement le dépôt du run, critères et dépendances existants, pas de cycle, chemins relatifs) ; avec des `questions`, l'étape du plan est bloquée jusqu'à `team_revise`. Réponse absente ou invalide, erreur de l'agent ou écart bloquant : une seconde tentative (nouvelle session, le motif en retour), puis l'étape est bloquée ; rapport `blocked` ou `failed` : bloquée tout de suite. Une tâche travaille dans son propre worktree détaché `<data>/team/<run>/<tâche>`, créé depuis le HEAD du worktree du run ; à la fin, TermF commite (`<ticket> <tâche>: <but>`, identité git de l'utilisateur, hooks du dépôt compris), applique les contrôles (un marqueur de conflit laissé fait échouer le commit), fusionne dans le worktree du run puis retire le worktree de la tâche ; en cas de conflit, TermF fusionne le travail du run dans le worktree de la tâche, y laisse le conflit, mesure désormais la tâche depuis ce travail et relance son agent pour le résoudre (correction automatique, puis toi). Jusqu'à `max_parallel_agents` agents à la fois ; deux tâches dont les `files_hint` se recoupent (ou dont l'une n'en a pas) ne tournent jamais ensemble. `shell` : la commande par le shell de connexion dans le worktree du run, avec l'environnement de sa préparation, 30 min au plus, bloquée si elle échoue. `rules` : le résumé de ce que les règles ont trouvé. `visual` (en attendant la phase 5) : une gate si une règle `ui-changed` au moins `warn` a vu l'interface changer, sinon sautée. `connector` : une gate ; la livraison reste `tickets_deliver` en deux temps. Budget du run : coût = somme des sessions de ses étapes ; dès qu'il l'atteint, ses agents sont arrêtés et l'équipe passe en `budget`. Reprise : au démarrage de l'app, une équipe qui travaillait passe en `paused` (rien ne dépense sans toi) ; `team_start` reprend chaque étape en cours : son tour fini est traité, sinon sa conversation reprend (`--resume`) avec un message « continue » ; avec un nouveau budget, elle repart plutôt dans une nouvelle session (avec ce message en retour, sans compter comme correction), dont le plafond suit le nouveau budget.
Règles (§7.6) : niveau de chaque règle = le sien si la bibliothèque l'active (sinon `off`) → `[rules]` de `termf.toml` → `[rules]` du workflow → `[rules]` du projet → ticket (`options.rules`, `team_rules` sans tâche) → tâche ; une règle d'un dépôt reste `off` tant qu'elle n'est pas activée. Les niveaux vont aux sessions (`rules`, donc dans leur prompt), et les contrôles des règles qui visent le rôle (`applies_to`) au niveau `warn` ou `block` tournent à la fin de chaque tâche : `scope` (fichier hors des `writes` du rôle, ou hors des `files_hint` de la tâche sans être cité dans le rapport ; diff de plus de 200 / 800 / 3000 lignes pour S / M / L : signalé seulement), `text-changes` (heuristique ligne à ligne sur `git diff -U0` : littéraux qui se lisent comme du texte, texte entre balises, valeurs `alt` / `title` / `placeholder` / `aria-label`, lignes Markdown, valeurs des traductions json / yaml / po, commentaires existants modifiés ; un texte retiré et ajouté dans le même fichier n'a fait que bouger ; tests, snapshots et lockfiles exclus ; justifié s'il figure dans le ticket ou dans `report.text_changes`), `ui-changed` (tsx, jsx, vue, svelte, css, scss, html…, traductions, `ui_impact` ou `affected_views` : la gate visuelle). `block` fait échouer l'étape (correction automatique puis toi), `warn` signale (événement `violation`, `Step.violations`, résumé à l'étape `rules`), `advise` ne fait qu'injecter les consignes.
Données : `<data>/termf.db` (tables `team_runs`, une ligne JSON par run écrite seulement par l'app, et `team_events`), lignes `team` ajoutées à `runs/<id>/journal.md`, worktrees des tâches dans `<data>/team/<run>/`. CLI : `termf team ls | plan <run> | run <run> [--workflow <nom>] [--rule <règle>=<niveau>]… [--budget <usd>] | status <run> | events <run> [--after <n>] | approve <run> <étape> | revise <run> <étape> <retour>… | rules <run> [--task <id>] <règle>=<niveau>… | stop [<run>]` (`ls`, `status` et `events` lisent la base, sans l'app). Essai réel : `cargo test -p termf-team -- --ignored real_team` (rôles sur Haiku, quelques centimes). Détails : `crates/termf-team`, `app/src-tauri/src/team.rs`, `crates/termf-cli/src/team.rs`.

### Contrats des rôles et des squads (phase 4, paliers S0 + S1)

Catalogue livré (`library/roles/`) : `cto`, `lead`, `po`, `pm`, `architect`, `ux`, `front`, `back`, `devops`, `qa`, `seo` (SEO technique, JSON-LD, Open Graph et image OG, Lighthouse ; soumis à `no-text-changes`), `secops`, `reviewer` (revue de code, voir plus bas). `orchestrator` devient `lead` et reste un alias partout : un rôle demandé sous l'un ou l'autre nom prend le fichier de la couche la plus précise des deux (une surcharge `orchestrator.md` de l'utilisateur gagne donc sur le `lead` livré ; un rôle d'un dépôt ne remplace jamais l'autre nom), `applies_to`, `[roles.orchestrator]` et les tâches d'un plan l'acceptent. Clés de frontmatter : `plannable: false` (po, pm, lead, cto, secops, reviewer : jamais proposés au planificateur, refusés dans une tâche), `credits` (sources des passages repris, lue par TermF, jamais dans le prompt ; avis dans `library/THIRD_PARTY_NOTICES.md`). `qa` n'écrit que dans des globs de tests (`writes`, à resserrer par projet). Workflows : `default` planifie avec `lead` ; nouveau `squads.toml` (`extends = "default"`, étape `plan` par `cto`).
Projet (`projects/<id>.toml`, lu par `termf_core::squads::load_team`) : `[team] staff = [rôles]` (chaque rôle une fois) ; `[[squads]]` avec `id` (lettres, chiffres, `-`, `_`), `lead` (`lead` par défaut), `roles = {rôle = effectif}` (sessions simultanées au plus ; ou `[squads.roles.<rôle>]` avec `count`, 1 par défaut, et les réglages du rôle dans la squad), `repos` (noms des dépôts du projet, vide = tous), `paths` (globs relatifs au dépôt, vide = tout), `domains`, `max_parallel` ; clé inconnue = erreur. Sans `[[squads]]` : une squad implicite `main`, tous les rôles, sans limite (rien ne change pour un petit projet).
Réglages d'un rôle sans toucher son prompt : `[roles.<rôle>]` dans `termf.toml`, puis dans le TOML du projet, puis `[squads.roles.<rôle>]` de la squad de la session, puis `[roles.<rôle>]` de `<dépôt>/.termf/project.toml`, par-dessus le frontmatter. Clés : `model`, `effort`, `effort_range` (`[bas, haut]`), `permission_mode` (remplacés) ; `skills`, `preferences`, `writes`, `deny`, `allowedTools`, `disallowedTools` (listes : `+x` ajoute, `-x` retire, une liste avec un nom nu remplace) ; toute autre clé (un texte de prompt) est une erreur qui renvoie aux préférences. Une liste vide remplace aussi ; une liste remplacée n'a plus que l'origine de sa couche. Le dépôt ne peut que choisir `model`, `effort`, `effort_range` et ajouter à `deny` / `disallowedTools` (jamais vider une liste) ; son `.termf/project.toml` invalide est ignoré avec un avertissement. Un rôle d'un dépôt non activé est écarté quand une autre couche a le rôle (ou son ancien nom) ; seul, il reste refusé. Les `skills` et `preferences` qu'un rôle nomme viennent avec ses sessions même éteintes (jamais celles d'un dépôt non activées). Pour une tâche, l'effort reste celui de sa taille borné par `effort_range` ; `effort` vaut pour les étapes hors tâche.
Plan (annexe A) : chaque tâche a `squad` (requis par le schéma ; `""` = la seule squad quand il n'y en a qu'une, sinon un rôle du staff ; un rôle du staff que la seule squad n'a pas reste au staff). `check_plan` refuse un rôle qu'aucune tâche ne peut avoir (`plannable: false`, hors des squads et du staff quand le projet en déclare), une squad inconnue, un rôle hors de sa squad, un dépôt hors de ses `repos`, une tâche sans squad dont le rôle n'est pas au staff ; un `files_hint` hors des `paths` de la squad est seulement signalé (événement `violation` à l'étape du plan). Brief : le planificateur reçoit `## The squads` (id, rôles et effectifs, dépôts, chemins, domaines, puis le staff) et seulement les rôles affectables ; un membre reçoit « You work in squad <id>; its paths: …; its domains: … ». `SessionSpec` gagne `squad?` (ses réglages de squad, et les préférences et règles `applies_to: [squad:<id>]` ; sans rôle, une préférence ou une règle `squad:<id>` ne vaut que dans cette squad) ; si les squads du projet ne se lisent plus pendant un run, l'étape d'une tâche est bloquée plutôt que traitée sans squad ; une tâche d'une squad le porte (`main` pour la squad implicite), un rôle du staff non. Règle `scope` : un fichier doit être dans les `writes` du rôle (tels que les couches les font) et dans les `paths` de sa squad. Ordonnanceur : au plus `max_parallel` tâches d'une squad et `effectif` tâches d'un rôle dans une squad à la fois, sous `max_parallel_agents` du workflow.
Commande : `team_squads {project}` → `{declared, squads: [{id, lead, roles: {rôle: effectif}, repos, paths, domains, maxParallel, members: [Member]}], staff: [Member]}` (le lead en premier dans `members`, puis les rôles de la squad, ou tous les rôles affectables quand elle n'en nomme pas) avec `Member = {role, lead, count, description, layer, plannable, credits, settings: [{key, value, from: ["role"|"global"|"project"|"squad"|"repo"]}], error}`. CLI : `termf team squads [<projet>]` (tous les projets par défaut ; chaque rôle avec `clé=valeur [origines]`). Vue Équipe : section Squads en lecture seule (cartes des squads et du staff, détail des réglages d'un membre au clic).

### Contrats de l'interface des runs d'équipe (phase 4b, ARCHITECTURE §6–§7)

Backend : `tickets_run` gagne `session?` (`false` : le run est créé — résolution, worktree, préparation, brief — sans ouvrir sa session Claude Code, puis `run-updated` ; pour une équipe, qui travaille dans ce worktree : une session lancée avec son message d'amorce y travaillerait en même temps). Comme avec une session, refusé sans API locale ou sans CLI `termf` (`run_guard`). Un tel run n'a pas de `claudeSession` (`Tickets::start_without_session`), donc rien à reprendre. Aucune autre commande ajoutée : tout passe par `team_*`, `team-updated` et `team_squads`. Les sessions de l'équipe ont, comme la tuile d'un run, le hook `PreToolUse` `termf guard` en plus de `--disallowedTools Bash(git push:*) Bash(gh pr:*) Bash(termf:*)` (voir la revue de code plus bas).

Notification système (fenêtre en arrière-plan seulement, regroupée par mise à jour) : une étape qui passe en `waiting` (gate), une étape nouvellement `blocked`, l'équipe `done` ou `budget`. Le compteur « en attente » de la navigation, la commande « prochaine session » de la palette et `⌘J` (`nextWaiting` : tuiles, puis sessions headless, puis runs d'équipe ; depuis la conversation affichée, sinon le run d'équipe affiché, sinon la tuile active) comptent aussi les runs qui attendent.
Vue Équipe (supprimée par la passe UX n° 3, T4 : le détail est la page Run, la liste Tickets > Runs) : onglets « Rôles et agents » (le contenu d'avant : en service, squads, rôles) et « Runs » (`TeamRuns`, `.split` liste | détail). Liste : runs du projet courant, plus récents d'abord, avec ticket, workflow, coût / budget, étapes à nommer (`current`) et état (`running` En cours, `waiting` attend ta réponse, `paused` en pause, `stopped` arrêtée, `budget` budget épuisé, `done` terminé). ### Contrats du triage du CTO et du questionnaire (phase 4, `phase4/cto-entry`)

Triage : tout run d'équipe commence par l'étape `triage` (agent, rôle `cto`, `--json-schema` = `termf_team::route::schema()`), puis la gate `approve-route` ; le workflow ne s'ajoute qu'une fois le routage appliqué. `[team] triage = false` (TOML du projet, sinon `termf.toml` ; `true` par défaut) garde l'ancien chemin. Modèle et effort du triage par `[roles.cto]`. Le brief du triage donne les workflows du projet (chaque étape avec son type, son rôle, et `optional: on|off`), les squads (avec leur lead) et le staff, tous les rôles avec leur description, ce qu'il faut rendre, puis la demande encadrée comme donnée non fiable (« written in TermF » pour une demande libre). Tant que le CTO trie, `TeamRun.workflow` est celui du lancement (celui choisi, sinon celui du projet, sinon `default`).
`Routing = {kind: "urgent-bug"|"bug"|"feature"|"epic"|"refactor"|"infra"|"seo"|"docs"|"other", size: "S"|"M"|"L", reason, workflow, skip: [étape], add: [étape], efforts: [{step, effort}], squads: [id], questions: [Question], budget_usd, changed}` (clés en snake_case ; `changed` : posé ou modifié par toi). Revérifié par TermF : workflow parmi ceux du projet (ceux de la bibliothèque, ceux d'un dépôt seulement activés, `squads` seulement si le projet déclare des squads, plus celui choisi au lancement), `skip` / `add` seulement des étapes `optional` de ce workflow et jamais les deux, rôle d'une étape ajoutée connu de la bibliothèque, `efforts` seulement sur des étapes d'agent qui tournent, squads existantes et une seule fois, `budget_usd` ≥ 0, questionnaire valide ; invalide : une correction, puis l'étape est bloquée. Ce qui ne change rien (sauter une étape déjà coupée, ajouter une étape déjà active) est retiré. Un workflow choisi au lancement (`options.workflow`, `TeamRun.workflowChosen`) est gardé quoi que réponde le CTO. Avec des questions, le triage est `blocked` et le run `waiting` jusqu'à `team_answer` (ou `team_revise` en texte libre, ou `team_route`).
Gate `approve-route` : décidée par le workflow **du lancement**, jamais par celui que le CTO choisit (un ticket non fiable peut l'y pousser) : toujours ouverte si le workflow routé a moins d'étapes `gate` que celui du lancement (`hotfix` routé depuis `default`, par exemple) ; sinon `[team] approve_route` du projet, sinon la clé racine `approve_route` du workflow du lancement (`hotfix` : `false` ; une couche de dépôt ne peut pas la régler), sinon `[team] approve_route` de `termf.toml`, sinon `true`. Coupée : `skipped` (« workflow X does not ask you to approve its routing ») et le routage s'applique aussitôt. `team_approve {run, step: "approve-route"}` l'applique tel quel ; `team_route {run, routing, budget?}` → `TeamRun` met ton routage à la place (seulement quand la gate attend ou que le triage est bloqué ; sans questions ; mêmes vérifications ; `changed: true`) : son `budget_usd` ne fait que baisser le budget du run, comme le conseil du CTO ; `budget`, ton montant, le remplace, même au-dessus de celui du lancement, et doit dépasser ce qui est dépensé ; refuser = `team_stop` (l'interface demande confirmation), et `team_start` remet la gate en attente. `team_revise` sur la gate relance le triage avec ton retour ; le triage ne se relance plus une fois le routage appliqué, et « Demander des modifications » sur une gate du workflow routé ne remonte jamais au triage (`no agent step comes before <gate>: approve it instead` si aucune étape d'agent ne la précède).
Application : les étapes du workflow routé (ses étapes facultatives selon `skip` / `add`) s'ajoutent après la gate (celles sans besoin dépendent de `approve-route`) ; l'étape du plan est faite par le lead (`lead` de `[[squads]]`) de la seule squad nommée, par `cto` s'il y en a plusieurs, par le rôle du workflow s'il n'y en a aucune ; `Step.effort` (nouveau) = l'effort du routage, borné par `effort_range` du rôle ; `run.workflow`, `maxParallel` et `workflowRules` sont ceux du workflow routé ; le budget du run devient le plus petit entre celui du lancement (le tien, sinon celui du workflow du lancement) et `budget_usd`, si ce conseil dépasse ce que le triage a dépensé. Les squads nommées valent pour tout le run (brief du plan, `check_plan`, ordonnanceur, contrôles des tâches) ; avec une seule, la squad `""` d'une tâche est elle. Un workflow qui a une étape `triage` ou `approve-route` est refusé à l'application. Événements `routed` (décision, budget du run, « set by you ») et `answered` ; les briefs des étapes suivantes commencent par « The request was routed as <kind>, size <S|M|L>: <raison> ».
Workflows livrés : clé d'étape `optional` (le routage peut l'activer ou la sauter ; `enabled` est son état par défaut) ; `default` gagne `prd` (pm, coupée), `frame` (po, active), `architecture` (architect, coupée) et `ux` (ux, coupée) avant `plan`, et `seo` (seo, coupée) en revue après `rules`, à côté de `security` ; `hotfix` a `approve_route = false`. `team_workflows {run}` → `[WorkflowView]`, ce que voit le triage de ce run : `WorkflowView = {name, description, steps: [{id, kind, role, optional, on}]}` (dans l'ordre, les facultatives comprises ; `on` : active par défaut).

IPC : `TeamCall::Start {run?, request?, options}` (`run` facultatif désormais) et `TeamCall::Answer {run, step, answers, note}`.
Questionnaire (un seul mécanisme pour le triage, le PM, le PO, le plan et toute étape qui rend `blocked`) : `Question = {id, theme: "product"|"scope"|"interface"|"technical"|"security"|"delivery"|"other", question, why, kind: "choice"|"multi"|"bool"|"text", options, proposed: [valeur], implications: [texte]}` ; schéma réutilisable `termf_team::plan::question_schema()` / `questions_schema()`, dans `plan_schema()`, `report_schema()` et `route::schema()` (champ `questions`). La doc officielle (code.claude.com/docs/en/hooks, lue le 2026-11-22) décrit la forme exec (`args` : programme lancé sans shell, un argument par élément) et le code 2 qui bloque un `PreToolUse` ; elle ne liste pas `--settings` parmi les emplacements des hooks mais s'en sert pour les régler (`--settings '{"disableAllHooks": true}'`) : c'est l'essai réel qui prouve que Claude Code applique un hook passé par `--settings` (la sortie de l'outil montre « PreToolUse:Bash hook error: [<termf> guard]: … is refused »).

Rôle `reviewer` (livré) : lecture seule (`disallowedTools: Edit, Write, NotebookEdit`), opus / high (`effort_range` medium–xhigh), `plannable: false`, `credits` superpowers (MIT, `THIRD_PARTY_NOTICES.md`) ; modèle et effort par `[roles.reviewer]`. Il cherche d'abord les bugs, puis les écarts aux conventions (`CLAUDE.md`, règles actives, seulement là où elles s'appliquent), le code inutilement compliqué et les tests sans valeur ; il ne croit pas les rapports ; une passe qui trouve, puis une validation de chaque constat à part (sous-agent pour un doute), faux positifs écartés (code non touché, ce qu'un linter ou les contrôles trouvent, style, échec hypothétique). Pas soumis à `no-text-changes` : il ne modifie rien. Le CTO (`cto.md`, une ligne ajoutée) ne laisse un constat sans correction qu'avec ton accord et sa raison.

Workflows : nouveau type d'étape `review` (une session d'un rôle comme `agent`, `role` requis, effort réglable par le routage) et clé d'étape `rounds`. `default` : `rules` → `review` (reviewer) → `security`, `seo`, `visual` (qui en dépendent désormais) → `deliver` ; `hotfix` : revue courte (`rounds = 1`, bugs du correctif et ce qu'il peut casser seulement). Ordre : après toutes les tâches, la `qa` finale comprise, et après les contrôles, pour relire aussi les tests de la QA ; les contrôles repassent après chaque correction ; sécurité, SEO et visuel voient le code corrigé. La revue n'est pas `optional` : le CTO ne peut pas la sauter, seul `[team] review` l'éteint. « Demander des modifications » sur une gate qui la suit va, comme avant, à la tâche finie en dernier, jamais au relecteur.

Réglages (`[team]` du TOML du projet, sinon de `termf.toml`) : `review` (`true` par défaut ; `false` : étape sautée, « the code review is off »), `review_rounds` (1 à 10, 2 par défaut ; le plus petit avec `rounds` de l'étape), `review_nits = "report"|"fix"` (`report` par défaut). Une valeur invalide bloque l'étape avec l'erreur.

Un tour : la session reçoit `--json-schema` = `termf_team::review::schema()` = `{summary, findings: [{severity: "important"|"nit", file, line, scenario, fix, task}]}` ; son brief ajoute « ## The tasks » (id, rôle, but et fichiers changés de chaque tâche) et « ## Your earlier rounds » (chaque constat et ce qu'il est devenu), sans le questionnaire. TermF revérifie : résumé non vide, fichier relatif dans le dépôt, ligne ≥ 1, scénario et correction non vides, `task` = l'id d'une tâche du plan ou un rôle (celui d'une seule tâche la désigne ; d'aucune ou de plusieurs = pas de tâche claire ; ni l'un ni l'autre = réponse invalide) ; invalide : une correction, puis l'étape bloquée. Chaque constat reçoit un id (`F1`…) et un sort `fate` : `sent` (important avec une tâche claire, ou détail avec `review_nits = "fix"`, avant le dernier tour), `asked` (important sans tâche claire, ou au dernier tour), `reported` (détail), `left` (laissé tel quel), `superseded` (retenu quand tu as relancé la revue : jamais parti, le relecteur peut le signaler de nouveau). Les tâches possibles sont celles du plan qui ont une étape (seules listées au relecteur et proposées). Les tours se comptent depuis la dernière fois que tu as renvoyé le travail (`Step.reviewBase` : relance de la revue, réponse qui renvoie des constats, modifications demandées à une gate qui la précède), pas depuis le début du run. Sans `asked` : l'étape est finie, chaque tâche visée repart avec ses constats en retour (« The code review (round N) found what to fix… », nouvelle session, nouveau worktree depuis le travail du run), ce qui suit la tâche (foreach, contrôles, règles, revue, sécurité…) repasse en attente comme pour `team_revise`, puis la revue refait un tour. Avec des `asked` : rien ne part, l'étape est bloquée avec un questionnaire de TermF dans `report.questions` (un par constat : `choice`, `theme: "technical"`, options = ids des tâches + `leave`, proposé = la tâche du relecteur s'il y en a une, implications par option). `team_answer {run, step, answers, note?}` sur l'étape de revue : une tâche → le constat lui part ; `leave` (raison dans `note`) ou une réponse à toi (la raison) → `left` avec `reason` (sans raison : refusé, « say why F1 stays as it is… ») ; l'étape est finie et ce qui est `sent` part. `team_approve` (accepter telle quelle, avec une confirmation dans l'interface) laisse tout ce que ce tour retenait (`sent` et `asked` → `left`) ; `team_revise` (relancer le relecteur avec ton texte) le met de côté (`superseded`). Sans aucune tâche à qui renvoyer (pas de `foreach`), chaque constat important devient une question texte « pourquoi le laisser tel quel ? » (la réponse est la raison). Une revue qui ne vient pas après la tâche renvoyée l'attend quand même (la tâche est ajoutée à ses `needs`). Le CTO ne passe outre qu'avec l'outil MCP `answer`, donc derrière ta carte d'accord, avec sa raison.

Données : `TeamRun.reviews: [Review]` (absent d'un run plus ancien) avec `Review = {step, round, summary, findings: [Finding], at}` et `Finding = {id, severity, file, line, scenario, fix, task, fate: "sent"|"asked"|"reported"|"left"|"superseded", to?, reason?}` (`to` : la tâche qui corrige, ou corrigerait) ; `Step.kind` gagne `"review"`, `Step.rounds?` ; le `report` de l'étape de revue est son dernier tour (`summary`, `status` `done` ou `blocked`, `questions`), vidé quand elle repart. Événement `review` à chaque tour (« round 1 of 2: 3 finding(s), back to T1, T3, 1 listed », puis une ligne par constat), dans le journal. Conversation du CTO : chaque événement `review` donne une `notice` `about: "review"` (`detail` : le message, masqué) **sans réveil** (lue avec le message suivant) ; ce qui t'attend arrive comme avant en `blocked`, avec réveil. CLI : `termf team events <run>` montre les tours ; `termf team answer <run> review F1=T1`, ou `F1=leave --note <raison>`.

Interface : détail d'un run, sous l'étape de revue, un `<details>` par tour (le dernier ouvert) : « Tour N · 3 constat(s) · renvoyés à T1, T3 · 1 signalé(s) », le résumé, puis chaque constat (Important ou Détail, `fichier:ligne`, scénario, correction attendue, sort : Renvoyé à T1 (« Sera renvoyé à T1 » tant que le tour t'attend, `held`), À décider, Signalé, Laissé tel quel, Mis de côté, et « Pourquoi : … »), l'option `leave` affichée « Laisser tel quel » ; une revue bloquée s'affiche « La revue de code attend ta décision » avec le questionnaire, ses textes refaits en français à partir des constats. Conversation du CTO : encadré TermF « Run 7 · revue de code : un tour est terminé », « Ouvrir » mène au run. Logique pure testée par `pnpm test` : `rounds`, `tally`, `held`, `LEAVE`, types `Review`, `Finding`, `Fate` dans `team-run-logic.ts`.

Tests : faux `claude` (`termf-team`) : constats valides renvoyés à la bonne tâche puis deuxième tour propre, constats invalides redemandés, limite de tours → à toi puis accepté tel quel, constat sans tâche → questionnaire puis laissé avec sa raison (et un détail renvoyé avec `review_nits = "fix"`), `review = false`, étape refusée sans garde-fou. Essai réel : `cargo build -p termf-cli && cargo test -p termf-team -- --ignored --nocapture real_team` passe maintenant par le garde-fou et par la revue (0,058 $ pour 7 sessions le 2026-11-22 ; revue propre au premier tour).

### Contrats des bonnes pratiques appliquées aux rôles et au brief (`roles/best-practices`, `universal-research.md` §3.8)

Brief d'une étape (`termf_team`, `brief()`), dans cet ordre : la ligne d'en-tête (``Step `<clé>` of TermF run …``, que lisent les faux `claude` des tests) ; le ticket encadré `<ticket>` et sa mise en garde ; `## The plan` (et `## The tasks` pour la revue) ; `## What the earlier steps reported`, dans `<reports>…</reports>` et présenté comme des affirmations que personne n'a vérifiées ; `## What the user answered` ; `## Your earlier rounds` (revue) ; les listes où choisir (triage : workflows, squads, rôles ; plan : squads, `## The roles you may use`) ; puis la ligne du routage, `## Your task`, la squad, la consigne de l'étape, `## To address in this attempt` ; enfin `## How to work` ou `## What to answer`, et le questionnaire. Contrat commun des étapes qui rendent un rapport (`## How to work`, le seul endroit qui le dit, les rôles ne le répètent plus) : ne pas commiter, pousser ni ouvrir de PR (TermF le fait) ; le hors périmètre signalé, jamais corrigé ; obstacle (commande en échec, délai, paquet manquant : diagnostiquer et contourner) ou limite (outil refusé, fichier hors de ce que l'étape peut changer, décision que le ticket ne prend pas : s'arrêter, `blocked` avec ses questions) ; résumé « points clés d'abord, environ 300 mots au plus, sans terme inventé en route », dit aussi au plan et à la revue. La consigne du plan ajoute que TermF commite, merge et livre le travail de chaque tâche.
Plafond de tours : `SessionSpec.maxTurns?` (`--max-turns`, sessions headless seulement). Chaque étape d'équipe en reçoit un selon la taille de sa tâche, sinon celle du routage, sinon M : S 60, M 120, L 240 par défaut ; `[team] max_turns = { S = …, M = …, L = … }` du fichier du projet, sinon de `termf.toml`, taille par taille ; `0` = sans plafond ; `max_turns` qui n'est pas une table de clés `S`, `M`, `L` aux entiers de 0 à 4 294 967 295 bloque l'étape avec l'erreur ; un fichier qui ne se lit pas comme TOML ne plafonne rien (ses lecteurs habituels le signalent). Une étape arrêtée par son plafond (vérifié avec Claude Code 2.1.330 : `subtype: "error_max_turns"`, `terminal_reason: "max_turns"`, `errors: ["Reached maximum number of turns (N)"]`) suit le chemin d'une erreur : une seconde tentative qui reçoit ce message, puis l'utilisateur.
Journal des décisions du CTO : `Routing.rulings: [texte]` (requis par le schéma du triage, `[]` possible ; `[]` pour un routage enregistré avant), une ligne par décision, `Ruling: quoi — pourquoi — coût si faux`. Quand il y en a et que le triage finit (pas tant qu'il pose des questions), l'étape `triage` reçoit un `report` (`status: "done"`, `summary` = ces lignes) : le détail du run l'affiche comme le résumé de l'étape, les étapes suivantes le lisent dans `<reports>`, l'événement `step_done` le reprend. Un routage que l'utilisateur fixe (`team_route`) vide `rulings` et retire ce rapport. Quand le CTO planifie plusieurs squads, ses décisions ouvrent le résumé du plan (consigne de son rôle).
Bloc que `next dev` écrit : avant de commiter une tâche, TermF remet en l'état (`git checkout HEAD --`, ou supprime le fichier s'il est nouveau) chaque `AGENTS.md` ou `CLAUDE.md` du worktree dont le seul changement, lignes vides mises à part, est un bloc `<!-- BEGIN:nextjs-<nom> -->` … `<!-- END:nextjs-<nom> -->` (Next.js 16.3+, `packages/next/src/server/lib/generate-agent-files.ts`), sauf quand le ticket ou le but de la tâche nomme ce fichier (son chemin relatif entier, en mot isolé, sans tenir compte de la casse : `web/AGENTS.md` ne nomme pas `AGENTS.md`) ; pendant une fusion laissée à l'agent après un conflit (`MERGE_HEAD`), les fichiers qu'apporte le travail fusionné restent. Une ligne `<chemin>: TermF left out of this task's commit …` s'ajoute aux `out_of_scope_findings` du rapport de la tâche (visible dans le détail du run), après que les règles l'ont lu : elle n'explique jamais un fichier pour la règle `scope`. Un fichier dont un autre texte change aussi est commité tel quel, pour les règles. La livraison n'est pas concernée : l'utilisateur voit les fichiers avant de confirmer.
Bibliothèque : `scope-strict` et `no-text-changes` disent « rapport au statut `blocked`, la question dans le questionnaire » au lieu d'`ask_user`, qui n'existe pas. Rôles : contrat d'équipe retiré (`back`, `front`, `devops`, `seo`, `lead`, `cto`) ; consignes positives avec leur raison, la négation gardée pour les garde-fous et doublée de ce qu'il faut faire ; « Not for … » dans les descriptions de `front`, `back`, `devops`, `seo`, `ux`, `qa`, `architect` ; un `<example>` dans `po`, `lead`, `cto` ; `front`, `back`, `devops`, `seo` (et `qa`) lancent les commandes `Verify` de la carte de stack et mettent commande et résultat dans leur résumé, « change the code, never the test or a hard-coded value » ; `secops` en deux passes (trouver, puis confirmer chaque candidat : principal, ressource, effet), faux positifs écartés, catégories OWASP Top 10:2025 par identifiant seulement ; `reviewer` : mêmes consignes positives, méthode inchangée. `library/crutches.md` (livré, hors des éléments) : les « béquilles » à réexaminer à chaque nouveau modèle ; la veille l'ajoute à son prompt et critique (`outdated`) l'élément dont les modèles actuels n'ont plus besoin de la béquille. Les règles restent en français (§3.8 n° 16 laissé de côté : le propriétaire écrit ses règles en français).

### Contrats de la mémoire du projet et de l'expert (phase 4, ARCHITECTURE §7.2, §12.4)

Mémoire (crate `termf-memory`) : un index local par projet dans sa propre base `<data>/memory.db` (jamais le verrou d'écriture de `termf.db`, où écrivent les agents et l'équipe) : `memory_docs` (`project, source, key, stamp, title, locator, at, size`, unique par `(project, source, key)`), `memory_fts` (FTS5 `title, body`, `unicode61 remove_diacritics 2`, `rowid` = le document), `memory_state` (`project, indexed, errors`). Sources (`Source`) : `claude` (conversations Claude Code des dépôts du projet et de leurs worktrees : les `*.jsonl` des dossiers de `<dossier Claude>/projects/` qui appartiennent au dépôt, par son chemin et son chemin réel (`termf_claude::sessions::{folder_name, belongs}`) ; les 16 derniers Mio lus, ligne à ligne, sans échouer sur une ligne inconnue ; seulement les messages `user` (hors `isMeta`, hors balises) et le texte des réponses `assistant`, chacun avec sa date, jamais les appels d'outils ni leurs sorties ; titre `custom-title` > `ai-title` > `summary` > premier message), `agents` (conversations headless de TermF du projet : `spec.project`, sinon le dossier ; messages `user` et `text`, hors sous-agents), `runs` (`runs/<id>/journal.md` des runs de tickets du projet ; plan, critères, tâches, rapports, questions, retours et notes de ses `team_runs`), `library` (`.md` et `.toml` de `<config>/projects/<id>/library/`, `<config>/projects/<id>/conventions/` et `<dépôt>/.termf/`), `memory` (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, `.claude/rules/**/*.md` des dépôts, mémoire automatique `projects/<dossier>/memory/*.md`), `docs` (fichiers suivis par git en `.md`, `.mdx`, `.markdown`, `.rst`, `.adoc`, `.txt`, hors `CLAUDE.md` et `CLAUDE.local.md`, 1 000 par dépôt), `git` (les 2 000 derniers commits de `HEAD` : message, auteur, date, fichiers touchés ; ceux qui manquent lus en un appel `git log --stdin --no-walk`), `artifacts` (entrées de `<data>/artifacts.json` dont le `cwd` est dans un dépôt du projet : titre, lien, dossier, date ; pas leur contenu). Incrémental : chaque source donne toutes ses clés avec une empreinte (date de modification en ns et taille, hash du commit, `updated`) ; seuls les documents dont l'empreinte change sont relus, ceux qui disparaissent sont retirés ; une source illisible garde ce qu'elle avait et dit pourquoi (`errors`) ; une source exclue, ou toute la mémoire si elle est désactivée, est vidée (`Memory::forget(settings)`, dans tous les projets) ; `index_all` vide aussi les projets retirés de la config. Tout texte (titre, provenance, corps) est masqué avant d'être écrit, hors de toute transaction, puis écrit par lots de 64 documents : valeurs du coffre s'il est ouvert (`Masker`), clés privées PEM (les lignes entre `-----BEGIN … PRIVATE KEY-----` et `-----END`), puis `termf_claude::mask::mask_text` ; le corps garde ses 256 derniers Kio. Recherche : chaque mot de 2 caractères ou plus (32 au plus) en préfixe, reliés par `OR` (rien de la syntaxe FTS5 ne vient de l'appelant), classement BM25 (titre × 4), extrait de 24 jetons, termes entre `[` et `]`, 50 résultats au plus, dans le projet demandé seulement, rien quand la mémoire est coupée ni d'une source exclue. Lecture : 24 Kio à partir d'un décalage en octets (ramené au début d'un caractère), `next` pour la suite, un document du projet demandé seulement. Réglages : `[memory] enabled = true`, `exclude = [source]` dans `termf.toml` (`termf_core::MemorySettings`, `save_memory`).
App : indexation de chaque projet 60 s après le démarrage puis toutes les 15 min, et du projet avant chaque question à l'expert, une à la fois. `memory_status {project}` → `Status = {project, enabled, indexed?, sources: [{source, included, docs, bytes, error?}]}` ; `memory_settings_save {project?, settings: {enabled, exclude}}` → `Status?` (vide aussitôt, dans tous les projets, ce que les réglages excluent, toute la mémoire si elle est coupée ; puis réindexe le projet donné ; source inconnue refusée) ; `memory_reindex {project}` → `Status` ; `expert_open {project}` → `AgentSession`. Ce que la mémoire rend à un agent (recherche, lecture) est masqué une seconde fois (coffre s'il est ouvert, motifs).
Expert : rôle livré `expert` (lecture seule, `plannable: false`, opus / high, `disallowedTools` Edit, Write, NotebookEdit, Bash, PowerShell, WebFetch, WebSearch). Une conversation permanente par projet comme celle du CTO (`cto::standing(app, project, role)`) : session `mcp`, rôle `expert`, sans budget, titre `Expert · <projet>`. Une session `mcp` de rôle `expert` a `--tools Read,Grep,Glob,Agent` (ses sous-agents ne font que lire) et des `--settings` qui n'autorisent que `mcp__termf__memory_search` et `mcp__termf__memory_read`, sans aucune action, et refusent Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch (« trifecta »). Une conversation permanente (CTO, expert) = `mcp` sans budget : seule épinglée, seule trouvée par `standing`. `@expert` dans la conversation du CTO va à la conversation de l'expert (jamais à une étape d'un run), et le CTO en est prévenu (`notice` `direct`) ; pendant un tour de l'expert, le message est gardé et part à la fin du tour comme message de l'utilisateur (`Agents::send_or_queue` → `true` ; plusieurs messages gardés partent ensemble), `cto_address` répond `via: "queued"` et le CTO reçoit une `notice` `queued` (« Message gardé pour expert : il le lira à la fin de sa réponse en cours »).
Outils de `termf mcp` par session : `termf_agents::mcp_tools(spec)`, écrits dans `mcp.json` (`TERMF_MCP_TOOLS`), seuls listés et servis par le serveur, revérifiés par l'app à chaque appel ; un serveur lancé sans `TERMF_MCP_TOOLS` sert ceux du CTO. Expert : `memory_search {query, sources?, limit?}` → `[{id, source, title, locator, at, snippet}]`, `memory_read {id, offset?}` → `{id, source, title, locator, at, size, offset, next?, text}`. CTO : ses outils et `ask_expert {question}` → `{answer, conversation, cost}` (outil de lecture : pas de carte ; 13 outils en tout). Un rôle dont les `allowedTools` contiennent `mcp__termf__ask_expert` (livrés : `po`, `pm`, `architect`, `cto` pour son triage et ses plans) : `ask_expert` seul, par `--mcp-config`, sans rien restreindre d'autre ; sans app pour le servir, l'étape tourne sans lui. `ask_expert` : réindexe le projet, puis `Agents::consult(spec, question, 15 min)` : une session `mcp` `expert`, titre `expert · <question>`, budget 1 $ au plus, la question pour premier message ; chaque demande de permission est refusée (« Nobody can approve this here ») ; au bout du délai, arrêtée ; son processus s'arrête avec la réponse (la conversation reste, non épinglée) ; réponse = `result` du tour, sinon son dernier texte ; budget épuisé, erreur ou délai : une erreur qui nomme la conversation.
API locale : `Call::Memory(MemoryCall)` : `reindex {project?}` → `[Status]` ; `ask {project, question, budget?}` → `{session, text, cost}` (jeton de l'utilisateur seulement : le `termf mcp` d'une session n'a que `Call::Mcp`).
CLI : `termf memory search <requête>… [--project <id>] [--source <s>]… [--limit <n>]` (lit la base, sans l'app ; par défaut le projet du dossier courant, chemins résolus), `termf memory reindex [--project <id>]` (par l'app ; tous les projets par défaut), `termf ask <question>… [--project <id>] [--budget <usd>]` (par l'app). Essai réel : `cargo test -p termf-cli --test mcp -- --ignored real_expert` (Haiku, de 0,003 à 0,006 $ pour deux tours le 2026-11-22 : `memory_search` et `memory_read` sur la mémoire d'un dépôt jetable, réponse qui cite la conversation et dit ce qui n'est pas vérifié ; puis un sous-agent lancé par `Agent`, qui n'a utilisé que Grep et Glob).

### Contrats des onglets et splits des Terminaux (passe UX n° 2, T6a)

Références : 1Password par `OP_SESSION_<compte>` (nom variable) non repris du shell de connexion (l'intégration à l'app 1Password ou un compte de service marchent) ; `aws-sm://` rend le `SecretString` entier ; une session réutilisable (agent de cache d'une CLI) qui garde la sortie ouverte laisse un fil bloqué jusqu'à sa fin. Interdits de `SECRET_DENY` : une défense en profondeur, pas une garantie. Une règle ne voit pas un programme appelé par un autre chemin (`/usr/bin/env`), ni dans `sh -c`, `bash -c`, `python -c`, `node -e`, ni un script que l'agent écrit puis lance, ni `ps eww`, `typeset`, `compgen -v`, `xxd .env`, `grep . .env`, `cp .env x` puis lecture, ni l'outil PowerShell (`Get-ChildItem env:`) ; `Read(**/…)` ne couvre que le dossier de la session (pas `../.env`, pas `~`). À l'inverse, `Read(**/.env*)` interdit aussi `.env.example`, `Read(**/id_*)` un fichier source `id_xxx`, `Bash(env *)` la forme `env VAR=x commande` (écrire `VAR=x commande`) et `Bash(cat *.env*)` un `cat` de `x.envrc`. Les `claude -p` d'outillage (veille, conventions, recette de worktree, assistant) gardent leurs réglages propres, sans ces interdits.
- Gestionnaire de mots de passe, tranche 1 (§3) : jamais lancé dans la vraie fenêtre (IPC simulé dans Chrome) ; `termf vault items|item` essayés seulement sur un coffre vide dans un `HOME` jetable. Pas de lecture de QR code (il faudrait une dépendance), pas d'import d'autres gestionnaires ni de synchro du coffre (tranche 3), pas de second facteur ni de Touch ID / Windows Hello (tranche 2), pas de pierre tombale pour une suppression. Si la relecture du fichier migré échoue, la copie `vault.v1.json` reste (un secret supprimé ensuite y resterait lisible avec le mot de passe maître) : ce chemin n'est testé qu'en appelant la vérification sur un contenu différent. Chaque code TOTP affiché ou copié écrit une entrée d'audit (`reveal`, `totp`) : deux par minute tant qu'un élément avec TOTP est à l'écran. Aucun outil ne donne encore un élément à un agent : l'option « utilisable par les agents » prépare les connexions et les recettes de la phase 6. La note s'affiche telle qu'écrite (Markdown non rendu). Une valeur révélée, copiée, générée ou tapée passe par la webview et l'IPC (copies non effacées, comme pour les secrets) ; titres et noms d'utilisateur sont dans le front (liste, palette) tant que le coffre est ouvert. Le générateur de phrases de passe suit une liste anglaise.
- API locale isolée (§3, « isolation de l'API locale ») : une défense en profondeur sur une même machine, pas une frontière de l'OS. Empêché : prendre le jeton de l'utilisateur à côté du socket ; le lire par Read, ou par `cat` / `head`… (en majuscules compris sous macOS), ou par une commande qui nomme `dev.termf.cli` ; afficher `$TERMF_MCP_TOKEN` (vérifié avec le vrai Claude Code, Haiku, avec et sans `termf guard`) ; réutiliser le jeton MCP d'une autre session lu dans son `mcp.json`, ou un jeton de tuile après la fin de son processus ; appeler les outils d'une session avec le jeton de l'utilisateur ; lancer, reprendre, livrer ou fermer un run, lancer une équipe, approuver une gate (revue visuelle comprise, quelle que soit l'écriture de la décision), accepter une demande de permission, démarrer une session headless, écrire dans une session (donc répondre à son invite) ou y ouvrir un agent par la CLI sans ta confirmation dans l'app ; démarrer par la CLI une session sans garde-fou, en `bypassPermissions` ou avec les outils de TermF ; exécuter une demande dont l'appelant est parti. Reste possible pour un processus de l'utilisateur décidé à le faire : lire le fichier sans nommer le dossier (glob `dev.termf.c*`, variable, script Python ou Node, `find`), ou en casse mêlée dans une commande Bash qui n'est pas une lecture de fichier reconnue (`python3 -c` sur `Dev.Termf.Cli`) dans une tuile sans `termf guard` ; puis parler au socket avec tous les droits sauf les actions réservées ; lancer `termf` lui-même, qui lit le jeton : les actions réservées attendent alors ta confirmation, mais pas `open` d'un shell seul, `agent send|interrupt|stop|takeover|handback`, `team answer|revise|rules|stop`, `review pr`, `schedule run`, `ask`, `memory reindex`, `vault lock|unlock` ; un rôle de ta bibliothèque qui fixerait lui-même `bypassPermissions` (le refus ne voit que la spec envoyée) ; lire son propre `TERMF_MCP_TOKEN` (il n'ouvre que les outils de sa session) autrement qu'en le nommant (`python3 -c 'import os; print(os.environ)'`), ou l'environnement d'un autre processus (`ps eww <pid>` sous macOS pour un binaire non système comme `claude`, vérifié ; `/proc/<pid>/environ` sous Linux) pour y prendre un jeton de tuile ou MCP vivant ; écrire `[api] confirm_cli = false` dans `termf.toml` (pris en compte au démarrage suivant seulement). Le bandeau ne peut pas dire qui demande : la CLI de l'utilisateur et un agent qui la lance sont indiscernables. Windows : fichier dans `%LOCALAPPDATA%` avec l'ACL héritée du profil (l'utilisateur, SYSTEM, Administrateurs), aucune ACL posée par TermF ; casse du chemin lu par Read non vérifiée. Jamais essayé dans la vraie app : le bandeau seulement en captures avec un IPC simulé.

Son jeton n'est plus dans `mcp.json` mais dans l'environnement de son processus, et le jeton de l'utilisateur n'appelle pas ses outils (voir la ligne ci-dessus pour ce qui reste possible). ## 5. Méthode de travail (à reprendre telle quelle)

- **Une tranche = un sous-agent** dans un worktree isolé, sur une branche `phaseN/<sujet>`, qui ouvre une PR et **ne merge jamais**. Brief autonome : sections du plan à lire, périmètre, fichiers partagés à toucher a minima, tests attendus, vérifications, livrable.
- **Revue** : `/code-review high <PR>` (medium pour de l'UI pure). Les constats repartent à l'agent auteur (il a le contexte), puis nouvelle CI.
- **Merge** : seulement si les 3 CI (macOS, Ubuntu, Windows) sont `SUCCESS` ; si `main` a bougé, `gh pr update-branch <PR> --rebase` puis CI à nouveau ; merge en squash, branche supprimée, worktree retiré.
- **Interface** : toute modification visible a sa page de captures avant/après (Chrome + IPC simulé, clair et sombre). Depuis le 2026-11-21, le propriétaire autorise le **merge automatique** après revue + CI 3 OS et fera **une revue groupée à la fin** : chaque page est copiée dans `.claude/reviews/<pr>-<sujet>.html` (exclu de git localement), à lui présenter ensemble en fin de travail. **Revue groupée en mode « swipe »** (demande du propriétaire, ARCHITECTURE §8.2) : artifact privé https://claude.ai/artifact/DJWDnJvH7KWSpP64od6veR ; réponses dans sa base, collection `decisions`, un document par carte `pr<N>-<écran>` (`decision: approve|reject|change|skip`, `comment`, `pins`) — les lire avec `ArtifactData list`. Générateur dans `.claude/reviews/tools/` (`manifest.json` : une ligne par PR, avec `only` = **2 à 4 écrans essentiels maximum** (le propriétaire ne peut pas tout revoir ; jamais les états vide/chargement/erreur) ; `build_deck.py` ; republier sur la même URL, voir `README.md`), captures durables dans `.claude/reviews/shots/<tranche>/`. Après chaque PR d'UI : copier ses captures dans `shots/`, l'ajouter au manifeste, reconstruire et republier. Pages HTML individuelles aussi gardées : `pr10-ssh-ui.html`, `pr11-sync-ui.html`, `pr13-context-reset.html`, `pr14-tickets-ui.html`. Laissé de côté par ces UI faute de commande Rust : retirer de l'agent une clé sans fichier, tester un dépôt avec son `core.sshCommand`, GitLab, clés `-sk`, cloner un dépôt manquant, oublier un appareil, `skipped` dans `Status` ; erreurs du backend en anglais.
- **Au plus 4 agents en parallèle** : le 2026-11-21, un kernel panic APFS (bug de macOS sous forte lecture parallèle de dossiers) a coupé la machine pendant que 8 agents compilaient ; garder la charge disque modérée.
- **Disque limité** : `cargo clean` dans chaque worktree terminé ; profil dev allégé ; pas de build release inutile.
- **Commits** terminés par les lignes `Co-Authored-By` et `Claude-Session` ; les règles de `CLAUDE.md` s'appliquent à tous (périmètre strict, demander en cas de doute, aucun texte modifié sans demande, rien de propre à une machine).
- Les secrets, le vrai `~/.ssh`, le vrai agent SSH et la vraie config ne sont **jamais** utilisés dans les tests : `HOME` et `SSH_AUTH_SOCK` pointent vers des dossiers jetables.
