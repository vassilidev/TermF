TermF/The team

The team: 29 agents, and you talk to one

Each agent is a Claude Code session with one job, its own model and its own permissions. You talk to the CTO: it reads your request, brings in the agents the ticket needs, and comes back to you at the key steps.

How they work together on a ticket

The same six steps as on the home page, with the agents behind each one. The amber steps wait for you: nothing moves on until you click.

  1. 1

    You ask the CTO

    CTO

    You describe the work in your own words, or pick a ticket. The CTO asks before it starts the team.

  2. 2

    The CTO picks the team

    CTO

    It picks the steps, the agents and the budget for this ticket, and shows you that route before anything starts.

  3. 3

    You approve the plan

    POPMUXARLE

    The product owner writes the acceptance criteria and asks what is still open, with proposed answers; the tech lead splits the work into tasks.

  4. 4

    Agents work in parallel

    FRBADESEOBRCODBAQA

    Up to four at once, each in its own copy of the repository. On medium and large tickets, QA comes last and proves each criterion.

  5. 5

    Checks, reviews, and the latest base

    RESECIN

    The repository's tests and rules run, then the code review and the security review. If the main branch moved on meanwhile, the merge integrator brings it in and resolves the conflicts.

  6. 6

    You approve the delivery

    You see the files and commits that will be sent, then the pull request opens.

The outlined marks join only when a ticket needs them: the product manager for a vague epic, UX when the interface changes without a design, the architect for a large decision, brand and copy when it asks for an identity or words, the database engineer for a migration.

Each card says what the agent does, when it is called, what it never does, the Claude model it runs on and how much effort it puts in, and what it may touch.

The CTO's tools and cost

The CTO is a role like the others, with one job: being the person you talk to. Each project has a permanent conversation with it, on the project's Home. It triages every team run, routes it or asks you first, relays what the team needs from you, and never writes code.

It reads the project's repositories with Read, Grep and Glob. It has no shell and no network, and it acts only through TermF's own tools: it can read the project, the runs, the tickets and what waits for you, and it can start a team run, answer a question, request changes, approve, stop, or send a message to a role. Every one of these actions waits on your approval card.

Two things are worth knowing about its cost. The conversation has no budget of its own, unlike a run. And every gate of a run wakes the CTO for one turn, so it can tell you what the gate is about; it runs on opus at high effort by default, which you can change with [roles.cto].

Each step of a run is a fresh Claude Code session with a brief: the role's instructions, the task, the criteria, your answers and the reports of the steps before. Turns are capped by the task's size, at 60, 120 or 240. Most planners and reviewers run on opus, most builders on sonnet, and the effort of a task follows its size, within the range of its role.

A role is a file

Every role is a Markdown file with a frontmatter, in the format of Claude Code's own agents. This is the start of the front-end role:

---
name: front
description: Front-end developer. Use for interface work — screens,
  components, styles, client-side logic, accessibility. …
runtime: claude-code
model: sonnet
effort: high
effort_range: [medium, xhigh]
---
You are the front-end developer of the team. You build the interface
the task asks for, with the project's own components and conventions.

You can change a role for every project, for one project, for one squad or for one repository, without touching its prompt, in [roles.<role>]: its model, effort and range, its permission mode, and its lists of skills, preferences, write paths and denied tools, where +x adds and -x removes.

[roles.front]
model = "opus"
effort_range = ["high", "xhigh"]
skills = ["+accessibility"]

A repository can only pick a model or an effort and add to what is denied; it can never widen what a role may do.

Squads

A small project needs nothing: one implicit squad has every role, with no limit. A bigger one can split into squads, a team per area of the project, each with its lead, its members and how many of each, its repositories, its paths and how many tasks it runs at once. The roles that serve every squad, like the product owner or the security reviewer, form the staff.

[team]
staff = ["po", "secops"]

[[squads]]
id = "billing"
roles = { back = 2 }
repos = ["billing-service"]
paths = ["src/**", "tests/**"]
max_parallel = 2

When a run spans one squad, its lead plans it; when it spans several, the CTO plans the batches, with the squads workflow, and each squad's lead splits its batch into tasks that TermF grafts into the run; a large batch waits for your approval. The setup assistant can propose squads when you create a project, and the project's Configuration has a squad editor.

The review loop

Once the tasks are merged and the checks have run, the reviewer reads the whole diff of the run. Each finding says where it is, what breaks and how to fix it, and it is either important or a nit. Important findings go back to the task that owns them, in a fresh session with the finding, and the reviewer looks again, up to two rounds by default. Nits are reported rather than fixed, unless you ask for fixes. A finding that no task clearly owns, or one still open after the last round, becomes a question for you; leaving it as it is asks for a reason, which stays in the run's report.

The security reviewer follows, on opus at extra high effort, in two passes: one to find, one to confirm, so you do not get false positives. Neither review can be skipped by the CTO; [team] review is yours to turn off.

The expert's memory

The expert answers from the project's memory first, then from the code. The memory is a local index in TermF's data folder. It holds the Claude Code conversations of the project's repositories and worktrees, the agents' conversations and the run logs, the library, the CLAUDE.md files and rules, the docs, and the last 2,000 commits; for claude.ai artifacts, the title and the link only. Secrets are masked before anything is written. It is indexed a minute after TermF starts, every 15 minutes, and before each question.

You can talk to it on the Home, switching the conversation from CTO to Expert, or with termf ask. The index stays on your machine; the passages the expert reads go to the model, as in any Claude Code session.

Budgets, stop and taking over

Each run has a budget, 15 dollars in the default workflow. Each step gets the smaller of its own budget and its share of what is left, and when the budget is spent, the agents stop and the run waits for you. The emergency stop interrupts every agent of a run, then stops them and kills their commands; you can start the team again afterwards. After a restart of TermF, a working team is paused, so nothing spends without you.

Between two turns, Take over opens any step's conversation in a terminal, with the same model, effort and permission mode; Hand back returns it to the team. There is never more than one process on a conversation.

What has been tried

With a real Claude Code, on Haiku, through automated tests: the triage, the plan, the tasks and their reports, the guard and the code review; the CTO's tools; the expert answering through ask_expert. With a fake Claude Code: the gates, the rules, resuming, the budget and the emergency stop. The interface: with a simulated backend, not yet in the app's real window. Brand, copy, motion and the specialists have not run in a real run yet. Not built yet: runs across several repositories, a squad editor, the leads' sub-plans.
