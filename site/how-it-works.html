TermF/How it works

How a ticket becomes a pull request

What happens between the moment you ask the CTO for something and the moment a pull request opens, step by step: who does what, what ships by default, and every place where the run waits for you.

TermF is not a model. It is the program around Claude Code that keeps the order of things: it starts each agent, gives it a brief, collects its report, holds the run at the gates and keeps the log. Agents never talk to each other directly. They talk through TermF, so everything they do is visible, can be interrupted, and has a cost you can see.

You ask the CTO

Every project opens on its Home, and the Home opens on a conversation with the CTO. It is a Claude Code session that stays open for the project: it knows the repositories, the runs, the tickets and what waits for you. You can ask it where something lives, where a run is at, or for a piece of work in your own words. Write @front to reach the front-end role instead, or @expert for the project expert.

The CTO reads, but it does not act on its own. It has Read, Grep and Glob, no shell and no network, and it works through TermF's tools: starting a team run, answering a question, approving, stopping. Each of these actions comes to you as a card in the conversation.

You can also start from the ticket itself: Tickets lists the inbox of every source the project follows, GitHub Issues, GitHub Projects, Jira Cloud or an MCP server, and “With the team” sits next to each ticket. Pasting a URL or a key works too, and so does termf team run from a terminal, which waits for your confirmation in the app.

The CTO picks the path

Every team run starts with a triage. The CTO reads the request and the project and decides how to handle it: what kind of work it is (a bug, a feature, an epic, a refactor, infrastructure, SEO, docs…), its size, which workflow fits, which optional steps to add or skip, the effort of each step, which squads take it, and the budget. It writes down its rulings with the reason and the cost of being wrong, and if something is unclear, it asks before it routes. TermF checks everything it proposes before using it.

That is the first gate. Nothing starts until you approve the path, change it, or refuse it. The hotfix workflow skips it for urgent fixes; if you launch with the default workflow and the CTO routes to a workflow with fewer gates, the gate opens anyway.

Workflows are files. The default one ships as library/workflows/default.toml. A project can write its own, starting from it with extends and writing only what changes, such as a different budget or a step turned off.

The product owner frames it

With the path approved, the product owner reads the ticket and the code, changes nothing, and writes the acceptance criteria, each with its source, and the list of what is out of scope. It explores the implications and the side effects, settles what the evidence settles, and turns the rest into questions for you.

When a ticket needs more, the CTO can add steps that ship turned off: a product manager writes a short PRD for a vague epic, an architect settles a design decision that crosses modules, a UX designer specifies the screens and their states before anyone builds them. The product owner, the product manager and the architect ask the project expert before searching on their own; it answers from the project's memory, with its sources.

Questions, with proposed answers

Whether they come from the triage, the product owner, the plan or a step that got stuck, questions reach you in one form. Each has a theme, the reason it is asked, the options, and a proposed answer already filled in. You change what does not suit you and send them all at once, or answer in free text. Your answers then travel with the run, into every brief that follows.

The lead plans, you approve

The lead turns the criteria into tasks, one per role: what each task covers, which files it expects to touch, what it depends on and its size. Tasks of the same level can run together; a task that needs another waits for it. The size sets the effort of the agent that will do it, medium, high or extra high, within the range its role allows.

That is the second gate. The plan waits for your approval in the run and on the Home. If something is off, ask for changes: the lead plans again with your feedback, in a fresh session.

The team works in parallel

Each task gets an agent of its role: a fresh Claude Code session, started by TermF with a brief that holds the criteria, your answers, the plan and the reports so far. The ticket itself reaches it as a framed file marked as untrusted data, never as instructions. A fresh session per step keeps each context small; the agent does not drag the whole history of the run along.

Every task works in a worktree of its own. When it is done, TermF commits it and merges it into the run's worktree; a conflict goes back to the agent. Two tasks expected to touch the same files never run at the same time, and at most four agents work at once in the default workflow.

You keep a hand on all of it. Each agent shows its state and its cost; @back sends it a message between turns; Take over opens its conversation in a terminal with the same model and settings, and Hand back gives it to the team again. The run has a budget, 15 dollars in the default workflow, split across the steps that are left, and the emergency stop interrupts every agent at once. If TermF restarts in the middle, the team waits, paused, until you start it again.

Checks and rules

When the tasks are merged, the repository's own checks run on the run's worktree, the lint, tests and build you declared for it, if any. Then come the project's rules. Three ship with TermF, off until you switch them on:

  • scope-strict: do only what the ticket asks; in doubt, stop and ask. Its check flags files changed outside the role's paths or the plan.
  • no-text-changes: no change to a visible or editorial text that the ticket did not ask for. Its check reads the diff for changed texts.
  • visual-review: a before and after review of every changed screen, as a gate.

Each rule has a level, from advise (instructions in the briefs only) to block (a deviation fails the step), and you set it per project, per ticket or per task. You can write your own rules, with a check of your own.

Review and security

The reviewer reads the run's integrated diff against the criteria, the contracts between tasks and the project's conventions. Each finding has its file and line, the scenario that breaks and the fix, and it goes back to the task that owns it; then the reviewer looks again, up to two rounds by default. A finding with no clear owner, or one still open after the last round, becomes a question for you. The CTO cannot skip the review.

Then the security reviewer goes over the same diff for vulnerabilities, abuse cases and vulnerable dependencies, in two passes, finding then confirming, so false positives are dropped before they reach you.

The visual review, when it is on

When the visual-review rule is on and the interface changed, the run stops once more. TermF's capture engine starts the project's dev server for the run and for its base, captures each changed screen with the system's Chrome, and compares the pixels and the texts. The page that shows those captures side by side is not built yet: today the gate asks you to look at the result in the run's worktree, then approve, ask for changes, or refuse.

You deliver

The last gate is the delivery, and it always happens in two steps. When the team is done, the run is ready to deliver. Deliver… shows you exactly what will be sent: the files to commit, the commits not pushed yet, and a fingerprint of that preview. Deliver commits that, pushes the branch and opens the pull request, with Closes #57 for a GitHub issue. If the worktree changed since the preview, the delivery is refused and you look again.

No agent can do this for you. Every session of a run carries TermF's guard, a Claude Code hook that refuses git push, pull requests and tracker writes, and a run does not start without it. From the command line, termf deliver waits for your confirmation in the app.

After the merge

TermF checks the pull request's state now and then. Once it is merged, the run is closed if nothing would be lost: its worktree, its local branch, its database copy and its ports go away. A pull request closed without a merge, or a session still busy, is only flagged as ready to clean up. And if the app restarted in the middle of a run, Resume picks up the same conversation, with the same environment, ports and guard.

What has been tried

TermF is in early development, and this is what is known to work. The path from the plan to the tasks, their reports, the guard and the code review has run with a real Claude Code, on Haiku, through automated tests; so have the CTO's tools and the expert. The gates, the rules, resuming, the budget and the emergency stop have been tested with a fake Claude Code. The interface has been checked with a simulated backend rather than in the app's real window, and Windows and Linux have been built and tested in CI but not run by hand. The full list of what is not verified is in docs/STATUS.md, in French.
