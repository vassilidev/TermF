TermF/Security

Security, and its limits

Agents that write code and run commands on your machine need guard rails. Here is each one TermF puts in place, what it stops, and what it does not.

Local-first

TermF has no server and no telemetry. It runs on your machine, and so does everything it keeps: projects, runs, logs, the project memory. Your code goes where Claude Code sends it, to the model, exactly as it would without TermF. The other connections are the ones you set up: GitHub or Jira for tickets, an MCP server if you add one, and the remote you pick for the sync.

The run guard

Every session of a run, the terminal of a ticket, each step of a team, and any step you take over, starts with termf guard as a Claude Code PreToolUse hook. It refuses git push in its forms (git -C . push included), gh pr, GitHub API calls that are not reads, writes to GitHub issues, starting or cancelling CI, and termf deliver, close and run, also when they hide inside sh -c, eval or $(…). A run does not start without it.

Delivery in two steps

Delivering a run is yours. Deliver… shows the files to commit, the commits not pushed yet and a fingerprint of that preview; Deliver commits exactly that, pushes and opens the pull request. If the worktree changed in between, it is refused. See Delivery in two steps.

The isolated local API

The app, the termf command line and the agents talk over a local API. Since an agent can run termf too, the API cannot trust whoever calls it:

  • Each terminal and each headless session gets its own token, with only the rights it needs, revoked when its process ends.
  • Your own token lives outside the agents' data folder, and the sessions TermF starts are denied reading it.
  • Starting a run or a team, delivering, closing, approving a gate, accepting a permission, typing into a session or opening an agent from the command line waits for your Allow in the app. The banner gives up after five minutes, and when the caller has left.
  • Some things are refused even if you allow them: an agent session without the guard, with every permission bypassed, or with TermF's own tools.

The banner cannot tell who is asking: your own command line and an agent that runs it look the same, which is why it says so. A few commands do not wait for confirmation: opening a plain shell, sending to an agent, interrupting or stopping it, taking it over or handing it back, answering a team's questions, asking for changes, changing a run's rules or stopping a team, posting a review on a pull request, running a scheduled task, asking the expert, reindexing the memory, and locking or unlocking the vault. Confirmation is on by default, [api] confirm_cli = true, read when TermF starts.

The CTO's session

The CTO talks to you and reads your repositories, and that is all its session can do on its own. It runs restricted, with Read, Grep and Glob only: no shell, no file edits, no web, no sub-agents, and only TermF's MCP tools, whose every action waits on your approval card. Its token reaches only its own tools. What it reads from tickets and from other agents comes to it marked as data.

Untrusted input, secrets

A ticket is written by someone else, and it may try to give orders. It reaches the agent as a framed file, marked untrusted, never as instructions; the reports of earlier steps are framed the same way in each brief.

The sessions TermF starts are denied .env files, private keys, /proc/*/environ and the usual ways of dumping the environment (printenv, env, export, declare -p…), along with TermF's own token folder.

Secrets at rest

The vault keeps secrets encrypted with Argon2id and XChaCha20-Poly1305, by scope, with prod asking the password again, an automatic lock after ten minutes and on sleep, and a hash-chained audit log; agents can never reveal a value. The settings sync is encrypted end to end the same way, with masked file names and a recovery key. SSH keys are read only from ~/.ssh, the files TermF wrote and the ones you pick.

What it does not cover

These guard rails are defense in depth on one machine, not an operating system boundary. A process set on getting around them still can. In plain words:

  • A script an agent writes and then runs, a git alias, or a tool other than Bash can still push or read a secret. The deny rules do not see every form: /usr/bin/env, sh -c, python -c, node -e, grep . .env, a copy of the file, or ../.env.
  • Claude Code settings managed by an organisation that allow only managed hooks, or that disable all hooks, would turn the guard off. This has not been tried.
  • A user process can still find TermF's token file by a pattern and use the API with every right but the reserved actions; it can also read another process's environment (ps eww on macOS, /proc on Linux).
  • On Linux and Windows, a vault key remembered in the system keychain can be read by any process of the user; on macOS, the keychain keeps it to the app.
  • The tool sessions TermF runs for itself, the scout, the conventions, the worktree recipe and the setup assistant, keep their own settings, without the secret denials.
  • The interface, the banner included, has been checked with a simulated backend rather than in the app's real window. Windows and Linux are built and tested in CI but have not been run by hand.

What was verified with a real Claude Code 2.1.330: the guard refusing git -C . push, an agent unable to print its own MCP token, and trusting repositories. Every known gap is listed in docs/STATUS.md §4, in French.
